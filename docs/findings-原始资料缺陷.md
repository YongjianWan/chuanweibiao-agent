# 原始资料的已知缺陷

> 本文件登记**甲方与公司提供的原始文件本身存在的问题**，不是我方代码的问题。
> 项目背景与术语在 `../README.md`（唯一入口）。
>
> **本文件的前四条只影响「评审点库」，而本项目已不使用评审点库**——
> 评分项与投标 PDF 由文件名尾部的 GUID 一一绑定（README §2.1），不需要评审点做中介。
> 所以前四条现在只对**换项目时的降级路径**有意义：若换到一个不按评分项拆分投标文件的项目，
> 需退回「评分项 → 评审点 → 检索关键词」的人工映射路线，那时才用得上。
> **第五条（PDF 跨页续行）与当前工作直接相关**，S0 从招标文件抽任何结构化内容都要处理。

## 1. 「②质量管理体系与措施」重复出现，总数 114 存疑

`评审点.md` 中「②质量管理体系与措施」出现了两次，第一次 7 项、第二次 31 项，
且前者是后者的子集。当前按 114 个评审点处理（两份都保留）。确认后总数可能变为 107 或 138。
`tests/test_s2_regression.py` 里有一条断言锁定了 114 这个数，澄清后需同步修改。
澄清这件事本身登记为 README §8 的 B7，已降级为非阻塞。

## 2. 大类编号错位，圈码与内容的对应关系不可靠

「④起重机械安全管理规范…」被排版成了大类，但从内容看它明显是
「③安全管理体系与措施」下的一个子项。这导致其后所有大类的编号顺延错位，
也就是说 本文第 6 节的圈码与内容的对应关系目前是不可靠的。同样归入 README §8 的 B7。

## 3. 评审点说明文字是模板套娃，实际信息量 = 114 个名称

`评审点.md` 里每个评审点的说明文字是同一段模板换名词生成的，
114 条全都是「基于招标文件及国家规范对 {X} 要求，总结…评审因素及评审点规则库…输出问题内容和判断理由」。
因此这份文档的实际信息量等于 114 个评审点名称。
**不要照着它写 114 个 prompt**，那会得到 114 个几乎一样的东西。真正的评分规则来自招标文件。

## 4. 早期样例是软件类标书，只能验证代码能跑、不能验证效果

早期样例投标文件（`原始资料/公司的临时样例文件仅作参考/`）是软件信息化类标书，
不是工程施工类。实测该文件中「分部分项」出现 0 次、「工程量」8 次，而「系统」5251 次。
在它上面测出的压缩比为 4 倍（140 万字压到 33 万字），因为检索词与文件内容领域不匹配，
命中的多是勉强凑上的章节。**该样例仅可用于验证代码能否跑通，不可用于验证效果。**
（压缩比本身也已不作为验收门槛，原因见 README §2 术语表与 §6 阶段一。）

## 5.（已解决，2026-08-20）从 PDF 抽表格必须处理跨页续行

核对招标文件评标办法时，
「各专业施工图设计的安排、协调、时间保证措施」一项的档位文本跨第 35/36 页分页
（`1.5-2` 断在页尾，「分」字落在下一页页首），按页取文本窗口会读进下一项的区间，
表现为**静默的假不一致**（比对结果显示 18/19，实际为 19/19）。
S0 从招标文件 PDF 抽取任何结构化内容时都需内建处理。

**2026-08-20 更新：已解决，且真身与上面记的不一样。** 抽 `criteria` 时看清了：
不是「`分` 字落到下一页页首」，而是表格**左列**的项名续行（`时间保证措施；`）
连同一行文档水印 GUID（全文 6 行），一起插进了**右列**正文的 `1.5-2` 与 `分` 之间。
两类噪声在原文里都独占整行，因此按行剔除即可，正文不需要字符级手术——
这一层认识把处理从「字符级手术」降成「删两类行」，实现见
`scripts/extract_criteria.py` 的 `load_clean_text()`，`verify_scoring_table.py` 复用同一份。
`python scripts/verify_scoring_table.py` 现输出 `档位一致 19/19`。

## 6. 评审点库的编号规则（仅降级路径需要）

**本项目用不到本节。** 仅当换到一个不提供结构化评分表的项目、需要退回
「评分项 → 评审点 → 检索关键词」的人工映射路线时，才需要这套编号。

评审点只有**两级**，没有第三级：

```
①施工组织设计                        ← 大类，用圈码 ①②③… 标识
  1）施工组织总体设计，方案针对性…    ← 子项，在本大类内从 1 开始编号
  2）施工现场平面布置和临时设施…
②质量管理体系与措施
  1）质量方针与目标体系
```

- **评审点 id = `大类圈码-子项序号`。** 例：`①-1` 指第①大类下的第 1 个子项。
- 全部 114 个 id 及其检索关键词见 `config/review_points.yaml`，由 `评审点.md` 自动生成。
- 圈码共 **11 种（①~⑪）、出现 12 次**——② 出现了两次，这是原始资料的缺陷，见 §9.1 与 §9.2。

## 7. `拆分评审项.xlsx` 表头第 9、10 列同名

表头 11 列为：

```
pb_item_guid | 评分名称 | 评分描述 | 要素id | 要素名称 | 要素描述 |
要素权重 | 二级id | 二级要素描述 | 二级要素描述 | 二级要素权重
```

**第 9 列与第 10 列都叫「二级要素描述」**，但第 9 列实际存的是二级要素**名称**
（如「原始任务书理解准确性」），第 10 列才是描述（如「准确复述并解析招标人所给
设计任务书中的关键指标、功能分区及特殊要求，无遗漏或误读。」）。

影响：用 `openpyxl` 按表头名取列会取到后者、静默丢掉名称列。按位置索引（第 9 列 = `r[8]`）
不受影响。当前代码都按位置取，不受此缺陷影响；**若将来改成按表头名取列，会静默出错。**

不向出题方追这条：xlsx 不进入运行流程（见 README §2.3），且按位置取列已可用。
