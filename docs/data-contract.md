# 数据契约

> 本文件是「工程建设类技术标辅助评审系统」**模块之间的全部接口规格**。
> 项目背景、术语定义、架构分阶段说明在 `../README.md`，那是唯一入口，本文件不重复。
> 读本文件前至少需要知道两件事：S0~S4 是五个处理阶段（README §3），
> 评分项与投标 PDF 由文件名尾部的 GUID 一一绑定（README §2.1）。
>
> **改这里的任何结构 = 改接口**，上下游要同步改；改其他任何东西都不影响别的模块。
> 字段名在文档和代码里必须一致——曾经出现过 `score` 一名两义（检索分 / 判分），
> 现在检索分叫 `match_score`，别改回去。

八个结构，按数据流顺序：

| # | 结构 | 谁产出 | 谁消费 | 落盘位置 |
|---|---|---|---|---|
| 1 | 章节块 | S1 | S2、页面⑤ | `data/projects/<slug>/sections/<bidder>/sections.json` |
| 2 | 章节块全量索引 | S1 合并 | S4 | `data/projects/<slug>/sections_all.json` |
| 3 | 评分表 | S0（离线） | S2、S3、页面② | `config/projects/<项目名>.yaml` |
| 4 | 项目特征摘要 | S0（离线） | S3 | 同上 yaml 内或同目录 md |
| 5 | 证据包 | S2 | S3、页面⑤ | `data/projects/<slug>/evidence/<bidder>/located.json` |
| 6 | 评审结果 | S3 | S4 | `data/projects/<slug>/reviews/<bidder>/*.json` |
| 7 | 报告数据 | S4 | 页面④、导出 | `data/out/` |
| 8 | 专家复核记录 | 页面⑤（人工） | S4、阶段三校准 | `data/projects/<slug>/expert_reviews.json` |

标注「**设计**」的字段表示该模块尚未实现，此处为约定；未标注的表示当前代码已产出。

## 1. 章节块（S1 产出）

当前实现基于 Word 标题层级；PDF 版切分策略见 README §3.7，代码尚未实现（README §8 的 B8）。

```json
{"id": "3#47",
 "file": "施工方案及技术措施123A9226-D66E-4ACE-8DC4-65A76A8282FA.pdf",
 "item_guid": "123a9226-d66e-4ace-8dc4-65a76a8282fa",
 "path": ["第二章 施工组织", "2.1 总体部署", "2.1.4 施工段划分"],
 "level": 3,
 "page": 12,
 "text": "本工程划分为三个施工段……",
 "char_len": 1840}
```

- `id` 格式为 `文件序号#块顺序号`，**只在单个投标人范围内唯一，不是全局唯一**。
  **`#` 后面是该块在本文件内的出现顺序（第几个），不是文档里的章节编号。**
  例：`3#47` = 第 3 个文件的第 47 个章节块，它的章节编号可能是「2.1.4」，写在 `path` 里。
  实测值形如 `6#11`。
- **跨投标人引用一律用 `(bidder, id)` 复合键，这是全系统所有引用的锚。**
  原因是 12 家共用同一套 20 个文件名、连文件名尾部的 GUID 都相同（README §2.1 的投标系统固定模板），
  而 `文件序号` 是 S1 本次运行时的位置序号——按家分别跑 S1，每家都从 `1#1` 重新开始。
  因此 `file`、`item_guid`、`id` 三者单独都区分不了投标人，必须带 `bidder`。
  合并时**不重写 `id`**，见下方「章节块全量索引」。
  （2026-08-19 决策。另一条路是合并时把 `bidder` 拼进 `id` 使其全局唯一，
  已否决：那样 `id` 会随合并顺序变化，断点续跑重跑一家就会让该家全部引用失效。）
- `item_guid`：**设计**。取自文件名尾部的 GUID（小写），把该块直接绑定到评分项，见 README §2.1。
  当前实现没有此字段，因为样例文件是 docx、不带 GUID。
- `path` / `level`：docx 路径来自 Word 标题层级；PDF 路径由行首编号形式给出，取值 1~5，见 README §3.7。
- `page`：**该块起始行所在的 PDF 页码，从 1 开始。** 页面⑤的「在原文中定位」靠它跳转。
  **T0 实现时必须一并输出**——切完再补要重跑 241 个 PDF。docx 路径无此字段，填 null。

## 2. 章节块全量索引（S1 合并产出）

S1 按投标人分别产出 `sections.json`，再用 `scripts/merge_sections.py` 合并成全量索引。
顶层为对象，内部 `sections` 数组的每个元素在单家章节块基础上注入 `bidder` 字段：

```json
{"project": "济阳区实验高级中学项目工程总承包（EPC）",
 "project_slug": "jiyang-epc",
 "schema_version": "1.0",
 "generated_at": "2026-08-19T17:28:00+0800",
 "bidders": ["sample-docx"],
 "sections": [{"bidder": "sample-docx", "id": "1#4", "file": "1",
               "path": [], "level": 4, "text": "...", "char_len": 652}],
 "stats": {"total_sections": 2121, "total_chars": 1405322,
           "by_bidder": {"sample-docx": {"sections": 2121, "chars": 1405322}}}}
```

- `bidder`：取值与 `manifest.json` 里的 `bidders[].id` 一致，真实场景为投标文件所在一级目录名。
- `id` 在单家范围内唯一；跨投标人引用时以 `(bidder, id)` 为复合键，合并时不重写。
- 这是 S1 -> S4 的汇总节点，S2 仍按单个 bidder 的 `sections.json` 独立跑。

## 3. 评分表（S0 产出，一个项目一份，人工确认过。设计）

顶层是一个映射，不是裸列表：项目级规则（招标文件里那些「适用于所有评分项」的话）
需要有地方安放，否则页面②录进去的整体规则无处可存。

下面的示例取自本次实测项目的真实数据（依据：实测）：

```yaml
project: 济阳区实验高级中学项目工程总承包（EPC）
source: 招标文件.pdf 第 33~37 页       # 这张评分表抽自哪里，人工确认时核对用
rules:                                 # 项目级规则，注入每次 S3 调用，对全部评分项生效
  - 内容不全酌情扣分
  - 若此条缺项不得分
items:
  - id: T-02                           # 评分项编号，本项目内唯一
    guid: 108d538f-85b8-4c7d-b32c-f6acdaa187b9   # 与投标 PDF 文件名尾部 GUID 相同
    name: 进度管理方案
    max_score: 4.0
    tiers:                             # 三档，按分值降序。每档是**区间**，不是单一分值
      - {tier: 优,   min: 3.0, max: 4.0, desc: ...}   # 最高档：闭区间 [3.0, 4.0]
      - {tier: 良,   min: 2.0, max: 3.0, desc: ...}   # 左闭右开 [2.0, 3.0)
      - {tier: 一般, min: 1.0, max: 2.0, desc: ...}   # 左闭右开 [1.0, 2.0)
    aspects:                           # 检索维度，仅供 S2 生成检索词，**不参与判分**
      - 施工进度计划编制与关键路径分析
      - 设计进度管理与协同机制
      - 进度保障措施与资源配置
      - 进度监测、预警与纠偏机制
    synonyms: [香蕉曲线, S曲线]         # 同义词扩展，补标书实际会用的说法。见 README §3.2 红线二
```

字段说明：

- **`tiers` 是区间不是单值。** 招标文件对全部 19 项统一写「分为一般、良、优，
  分别酌情得 X-Y 分、Y-Z 分、Z-W 分」。因此 `score` 是区间内的连续值，
  README §1 的 P0 红线「档位不能错」指的是**落错区间**，区间内的差异不作为错误。
- **区间边界归属：除最高档外一律左闭右开 `[min, max)`，最高档为闭区间 `[min, max]`。**
  招标文件原文写的是「1-2 分、2-3 分、3-4 分」，字面上首尾相接，2.0 同时属于两档。
  数据契约必须消歧，否则判出 3.0 分时 `tier` 填什么无定义，
  README §6 阶段三的「档位一致率」也算不出来。
  **这是我方的实现约定，不改变招标文件的分值范围。**
- `guid`：主键，把评分项与投标 PDF 绑定，见 README §2.1。缺它则退回人工映射路线。
- **`aspects` 是检索维度，不是评分维度。** 招标文件里没有这一层，由我方从评分描述推导，
  用途只有一个：给 S2 提供比评分项名更细的检索词（README §3.2 说明了为什么检索词粒度要细）。
  **它不带权重、不产出得分率、不参与 S3 判分**——2026-08-19 决策，理由见下方
  「为什么不做要素加权定分」。产出方式：大模型按统一 prompt 从评分描述拆 3~5 条，
  人工扫一眼即可，不求精确。离线产出，见 README §1.1。
- `rules` 与项目特征摘要都是全局上下文，但两者不可互相替代：摘要描述**这是个什么工程**
  （用于判「针对性」），`rules` 描述**判分时必须遵守的硬约束**（用于避免该扣的分没扣）。
  本项目的两条 `rules` 是招标文件原文，其中「若此条缺项不得分」使
  README §3.2 红线三的「未命中判 0 分」从设计选择变成招标方的明文要求。

### 为什么不做要素加权定分（已否决的设计，留档防止回潮）

早先的设计里 `aspects` 是带两级权重的「要素 / 二级要素」，各级权重和为 1.0，
S3 输出每个要素的得分率，加权后按 `score = tier.min + 得分率 × (tier.max - tier.min)`
决定分数在档位区间内的位置。**2026-08-19 否决，不要再往回加。**

否决理由是成本与收益不成比例：

- 成本：19 项 × 4 要素 × 3 二级要素 ≈ 230 条配置要离线产出并人工核；S3 的 prompt 变长、
  输出结构变复杂；多出「档位判定与得分率互相矛盾」这种边界态和对应的 confidence 乘数；
  页面⑤多一整块 UI。
- 收益：**只影响分数在档位区间内的小数点位置**。而档位本身由模型对着招标文件的
  档位描述原文判定，要素完全不参与——不参与的原因是让得分率定档位需要一组阈值
  （「0.61 属良、0.8 属优」），定阈值要有专家评分作基准，我方一份都没有，本次也不采集。

而区间内的小数点位置，恰好是客户明说不重要的部分：
「定 5 分还是 4 分不重要，这是精确度问题。但不能是 8 分，这才是核心问题。」（依据：录音）

**现行做法**：`tier` 由模型判定，`score` 由模型直接在该 `tier` 的区间内给出，
系统只校验 `score` 是否落在区间内（越界按 README §3.6 重试）。
可解释性由判分理由 + 引用证据承担，不由加权算式承担。

## 5. 证据包（S2 产出）

```json
{"item_id": "T-02", "item_guid": "108d538f-85b8-4c7d-b32c-f6acdaa187b9",
 "bidder": "中冶建工集团有限公司8010856",
 "name": "进度管理方案",
 "candidates": 32, "units": 3, "fallback": false,
 "evidence_chars": 2180, "budget": 2280,
 "picked": [{"section_id": "3#47",
             "file": "进度管理方案108D538F-85B8-4C7D-B32C-F6ACDAA187B9.pdf",
             "path": ["第二章 施工组织", "2.1 总体部署", "2.1.4 施工段划分"],
             "unit": ["第二章 施工组织", "2.1 总体部署"],
             "page": 12,
             "match_score": 21.7, "hit": ["t:关键路径", "b:施工段"],
             "chars": 1840, "truncated": false}
            ]}
```

> 示例中 `picked` 只列出 1 条，实际应有 `units: 3` 个证据单元、合计 `evidence_chars: 2180` 字，
> 其余条目已省略。字数与条目数在真实输出里必须自洽。
> `budget: 2280` 是 T-02（4 分项）按分值算出来的值，不是全局常数，见下方 `budget` 说明。

字段说明：

- `item_id` / `item_guid` / `bidder`：**设计**。当前实现无这三个字段，原因见 README §3.1。
  **`bidder` 的取值 = 投标文件所在的一级目录名，原样照抄，含尾部的投标编号**
  （例 `中冶建工集团有限公司8010856`，定义见 README §2 术语表）。
  它是下方报告数据里 `matrix` 与 `totals` 的键，**12 家写法必须完全一致**——
  截断、去空格或改写会把并排表拆成多列。T8 补齐该字段时按此取值。
  当前实现输出的是 `point_id`（评审点 id），本项目用不到评审点，见 README §2.1。
- 检索范围：**该评分项 `item_guid` 对应的那一个 PDF 内部**，不跨文件（README §2.1）。
- `candidates`：通过门槛的候选章节块总数。`units`：收取的证据单元数。
- `fallback: true`：走了降级检索（`aspects` 级检索不到，退到评分项名级），属弱证据，
  S3 需据此降低 `confidence`。
- `evidence_chars` / `budget`：本包实际字数 / 上限字数。顶到 budget 说明证据被截断，可能漏内容；
  远小于 budget 说明这项在投标文件里着墨很少。

  **`budget` 按分值分配，不是全项统一常数**（2026-08-19 决策）：

  ```
  budget_i = clamp(基准预算 × 项数 × max_score_i / 总分, 1500, 6000)
  ```

  基准预算 3000、19 项、总分 100 时，20 分的「设计任务书优化」得 6000（触上限），
  4 分的「进度管理方案」得 2280，3 分项得 1710，**19 项合计 51,600 字/家**
  （统一 3000 时为 57,000 字/家，略低于它）。

  理由：19 项分值从 3.0 到 20.0 不等，「设计任务书优化」占总分 20%，
  判错它一档的代价是 3 分项的 6 倍多，对应的 PDF 通常也最厚；
  给两者相同的证据字数是把精度平均分给了不等权的目标。
  总输入量与统一 budget 时同量级（因此不影响 README §6 阶段二的吞吐量账），只改分配。
  上下限是防止 3 分项被压到无法判断、20 分项一项吃掉大半预算。
  **基准预算 3000 由 T9 实测后重新标定**，代码位置 `src/s2_locate.py` 的 `BUDGET`。
- `picked`：按文档原顺序排列，**同一 `unit` 的块相邻**。`picked` 的数组下标即引用编号（README §3.5）。
- `section_id`：该块在章节块里的 `id`。**它只在单家范围内唯一**，回查原文时必须配本证据包顶层的
  `bidder` 一起用，即复合键 `(bidder, section_id)`，理由见本文件「章节块」的 `id` 字段。
- `unit`：该块所属证据单元的路径，即其直接父章节。
- `page`：透传自章节块，供页面⑤跳转 PDF 页用。
- `match_score`：检索匹配分，IDF 加权和，无上界，**仅用于排序和过滤，不参与判分**，
  与评审结果里的 `score`（判分）是两回事。低于 `MIN_SCORE`（当前 8.0）的块不进候选。
- `hit`：命中详情。前缀含义——**大写 = 完整短语命中，小写 = 单词命中；T/t = 命中标题链，B/b = 命中正文**。
  「短语」与「单词」的界线是可判定的：**短语 = 检索词条目本身**（评分表里的一条 `aspects`
  条目或 `synonyms` 条目），整条原样出现在文本里才算；
  **单词 = 该条目切分后的成分词**，单个成分出现即算。
  例：条目「施工进度计划编制与关键路径分析」整条出现记 `T:施工进度计划编制与关键路径分析`；
  只出现切出来的「关键路径」则记 `t:关键路径`。
  代码位置：`src/s2_locate.py` 的 `score_section()`，`phrases` 参数是短语、`terms` 是成分词。
- `truncated: true`：该块因 budget 用尽被截断，只取了前 `chars` 个字。

## 6. 评审结果（S3 产出，交付物的原子。设计）

```json
{"item_id": "T-02", "bidder": "中冶建工集团有限公司8010856",
 "status": "rated", "tier": "良", "score": 2.6,
 "cite": [0, 2],
 "reason": "有总体进度计划与关键路径，但设计与施工的进度协同机制未结合本项目 EPC 模式说明",
 "confidence": 0.7,
 "attempts": 1,
 "perf": {"in_tokens": 3400, "out_tokens": 180, "latency_ms": 8200}}
```

字段说明：

- `status`：`rated`（已评定）/ `unrated`（未评定，见 README §3.6）。
  `unrated` 时 `score` 必须为 null，**不得填 0**。
- `tier`：档位，**由模型判定**，依据是招标文件的档位描述原文 + 证据包 + 项目特征摘要。
  取值必须是该评分项 `tiers` 里的 `tier` 之一（一般 / 良 / 优）。
  **判错档位是 README §1 的 P0 红线**，档位内的分值差异不作为错误。
- `score`：判分，**由模型在 `tier` 对应区间内直接给出**，保留一位小数；
  或为 0（未命中，即证据包为空）。
  **系统校验 `score` 是否落在 `tier` 的区间内**（边界归属见上方评分表 `tiers`），
  越界与引用编号越界同等处理：判该次调用失败并重试（README §3.6）。
  为什么不用要素加权算这个值，见上方「为什么不做要素加权定分」。
- `cite`：引用的证据编号数组，取值为证据包 `picked` 的数组下标。原文由系统按此截取，模型不产出原文。
  编号越界视为本次调用失败，走 README §3.6 的重试。
- `reason`：判分理由。**这是可解释性的唯一承担者**，要求写明「判哪一档、为什么是这一档、
  差在哪」，而不是复述证据内容。客户明确要求报告里能扒出「哪项对应哪个得分点、
  偏差理由是什么」（依据：录音）。
- `confidence`：置信度，取值 0~1，越大越可信。起始 1.0，按以下**三个**减分因素相乘：

  | 代号 | 触发条件 | 乘数 |
  |---|---|---|
  | 降级 | 证据包 `fallback: true` | ×0.7 |
  | 截断 | 存在 `truncated: true` 的证据 | ×0.9 |
  | 重试 | `attempts > 1`（重试过才成功） | ×0.9 |

- **`confidence < 0.85` 的项在报告和界面上标记为「建议人工复核」**（页面④的 ⚠ 标记）。

  **阈值取 0.85 是算出来的，不是拍的。** 三个因素的全部非空组合共 7 种，按取值归并如下：

  | confidence | 对应组合 | 是否标 ⚠ |
  |---|---|---|
  | 0.900 | 仅截断；仅重试 | **否** |
  | 0.810 | 截断+重试 | 是 |
  | 0.700 | 仅降级 | 是 |
  | 0.630 | 降级+截断；降级+重试 | 是 |
  | 0.567 | 三者全中 | 是 |

  即阈值 0.85 等价于一条可读规则：
  **除「仅被截断」与「仅重试过」两种情形外，一律标 ⚠。**

  **改乘数或加新因素时，必须重算这张表并同步阈值。** 否则会出现阈值永远触发不到的情况——
  最初的 0.6 就是如此（当时三因素下唯一低于它的组合是 0.567）。
  这条规矩被违反过一次并留档：加入第四个因素「打架」（档位判定与要素得分率矛盾）时未同步本表，
  由一次冷读检查发现。该因素随「要素加权定分」在 2026-08-19 一并删除，本表已由四因素重算回三因素。
- `attempts`：实际调用次数，1 表示一次成功。
- `perf`：该次调用的性能数据，逐项累加即为 README §1 的吞吐量指标。

## 7. 报告数据（S4 产出，客户交付物的数据层。设计）

**渲染成什么文件格式（docx / PDF / HTML）取决于 README §8 的 B6，现在不定；
但数据结构现在就定死，渲染层换实现不影响上游。** T6 的验收只看这个结构齐不齐，不看长得好不好看。

```json
{"project": "济阳区实验高级中学项目工程总承包（EPC）",
 "generated_at": "2026-08-21T14:03:11+08:00",
 "bidders": ["中冶建工集团有限公司8010856", "…（共 12 家）"],
 "matrix": [{"item_id": "T-02", "name": "进度管理方案", "max_score": 4.0,
             "scores": {"中冶建工集团有限公司8010856": 2.6,
                        "济南一建集团有限公司8008754": null}}],
 "totals": {"中冶建工集团有限公司8010856": {"score": 78.4, "unrated": 0,
                                          "expert_score": 78.7, "expert_overrides": 1},
            "济南一建集团有限公司8008754": {"score": 55.0, "unrated": 1,
                                          "expert_score": 55.0, "expert_overrides": 0}},
 "details": ["<评审结果对象，全部，按 bidder + item_id 排序>"],
 "unrated": [{"bidder": "济南一建集团有限公司8008754", "item_id": "T-04",
              "attempts": 3, "last_error": "JSON 解析失败"}],
 "review_flags": [{"bidder": "济南一建集团有限公司8008754", "item_id": "T-02",
                   "confidence": 0.63, "why": "fallback 证据 + 重试过"}],
 "audit": [{"item_id": "T-07", "kind": "no_discrimination",
            "detail": "12 家全部判「一般」档", "tier_dist": {"优": 0, "良": 0, "一般": 12}}],
 "expert_reviews": ["<专家复核记录对象，全部，见本文件第 8 节>"],
 "perf": {"wall_clock_sec": 582, "concurrency": 8,
          "calls": 228, "retries": 2,
          "in_tokens": 412880, "out_tokens": 38210,
          "gpu": "未采集", "vram_peak_gb": null,
          "gpu_note": "模型为远程托管端点，我方进程内无法采集显存"},
 "compute_notes": {"owner": "<算力归属：我方自有 / 政务云 / 其他>",
                   "spec": "<卡型号、显存、可用卡数>",
                   "model": "<模型名与版本>",
                   "method": ["证据定位：IDF 加权 + 单锚点闸门，不依赖向量库",
                              "防幻觉：引用由模型选择证据编号，原文由系统截取"]}}
```

字段说明：

- `matrix[].scores` 里 `null` = 未评定（README §3.6），`0` = 投标人未写。两者必须在渲染层用不同符号
  （页面④用 `—` 和 `0`），**不得在数据层合并**。
- `totals[].score` 不含未评定项，`unrated` 给出该家有几项没判出来，供渲染层在合计旁注明。
- `review_flags`：`confidence < 0.85` 的项，即页面④的 ⚠。
- **`audit`：跨投标人的档位分布审计，S4 汇总时免费算出来。**
  触发条件一条：**某评分项在全部投标人中判分完全无区分**——12 家落在同一档（含全部 0 分）。
  招标文件为该项设了分值、12 家专业投标人写出完全同档内容的概率，
  远低于「该项检索配错了」或「该项的档位判飘了」的概率。

  **这条为什么必须有**：早先设计里 confidence 有第四个减分因素「打架」
  （档位判定与要素得分率矛盾），它是唯一一个能自动发现「档位判飘」的信号。
  砍掉要素加权定分时它一并消失了——而**判错档位是 §1 的 P0 红线**，
  不能只剩人工抽查。本字段是它的替代品，且比它便宜：不需要要素、不需要专家基准，
  纯粹由 12 家的档位分布算出来。

  它查的东西与 `review_flags` 正交：`review_flags` 是**逐项**的证据质量，
  `audit` 是**跨家**的判分区分度。两者都不查的那部分（单项判飘但 12 家分布正常），
  本次测试确实没有自动信号，只能人工抽查——这一点在报告里要如实说明，不要含糊过去。
- **`matrix[].scores` 与 `totals[].score` 只装系统判分，专家改判永不写进这两处。**
  交付给客户的报告主体是系统判分；专家改判走 `expert_reviews` 与 `totals[].expert_score`
  并排呈现，理由与后果见本文件第 8 节。（2026-08-19 决策）
- `totals[].expert_score`：专家口径合计。逐项取值——**该项有 `action: "改判"` 的记录就用
  `expert_score`，否则用系统判分**——再求和；与 `score` 同口径，未评定且专家未改判的项不计入。
  该家一条改判记录都没有时，`expert_score` 等于 `score`，不是 null。
- `totals[].expert_overrides`：该家 `action: "改判"` 的项数，供渲染层在专家合计旁注明。
- `perf.gpu` / `perf.vram_peak_gb`：采集不到时分别填 `"未采集"` 和 `null`，并在 `gpu_note` 写明原因。
  **不得省略这三个字段，也不得填估算值。** 见 `ui-spec.md` 页面③的同一条约定与 README §8 的 B3。
- **`compute_notes`：交付报告中体现「我方跑在什么算力上」的字段。**
  来源是明确的对外要求——竞品在政务云（三里屯）上测，我方用自己的算力，
  报告里要写清楚用的是什么。
  > 录音转写此处作「专利」（「咱们可以用自己的专利问题…测报告里头要体现一下咱们的
  > 什么专利，什么那个什么计专利」），**实为「算力」的转写错误**：前半句对应的是
  > 竞品在政务云上测、我方可以用自有算力，「计专利」是「算力」的二次转写。
  > 本项目**没有**要在报告里体现专利或软件著作权的要求，不要照字面去找专利号。
  - `owner`：算力归属，我方自有 / 政务云 / 其他。**这是与竞品对比时唯一的差异点，不能漏。**
  - `spec`：卡型号、显存、可用卡数，取决于 README §8 的 B3，解除后填实际值；
    拿不到就照 `perf.gpu` 的同一条规矩填「未采集」并写明原因，**不填估算值**。
  - `model`：模型名与版本，取决于 B2。
  - `method`：我方技术做法的说明性条目，由开发填写，内容须与实现一致。
    这里是「我们怎么做到的」，与 `perf` 的「跑成什么样」互补。

## 8. 专家复核记录（页面⑤人工产出。设计）

**这是本系统里唯一由人写入的结构。** 一条记录 = 一位专家对一个 `(bidder, item_id)` 的一次表态。

```json
{"bidder": "中冶建工集团有限公司8010856",
 "item_id": "T-02",
 "action": "改判",
 "system_score": 2.6,
 "expert_score": 2.9,
 "delta": 0.3,
 "note": "设计施工协同在 4.2 节有写，检索没取到",
 "reviewed_at": "2026-08-21T14:20:03+08:00"}
```

字段说明：

- `action`：`认可` 或 `改判`。`认可` 时 `expert_score` 等于 `system_score`、`delta` 为 0，
  **仍然要落一条记录**——「专家看过并同意」与「专家没看过」是两回事，阶段三校准要区分。
- `system_score`：**记录写入当时的系统判分快照**，取自评审结果的 `score`。
  冗余存一份是故意的：这条记录要能脱离报告独立解释，而系统判分可能因重跑而变。
- `delta` = `expert_score - system_score`，保留一位小数。
  **系统判分为 null（未评定）时 `delta` 记 null**，不记 0——差异无定义，不是没差异。
- `reviewed_at`：ISO 8601 带时区。同一 `(bidder, item_id)` 允许多条记录，
  **以 `reviewed_at` 最新的一条为准**，历史记录不删（阶段三要看专家自己改了几次）。

### 为什么改判不覆盖系统判分（2026-08-19 决策，留档防止回潮）

三条理由，任意一条单独成立：

1. **交付物口径必须唯一。** 报告是给客户的东西，「这 78.4 分是机器给的还是人改的」
   必须一句话答得上来。改判一旦回写进 `matrix`/`totals`，这个问题就没有答案了。
2. **埋点的目的是采集差异。** README §5.3 页面⑤要求改判记录落库，理由写的是
   「阶段三校准分数的数据来源」。差异 = 专家分 - 系统分，**两个值都留着才算得出来**；
   后者盖掉前者，等于把埋点的唯一用途做没了。
3. **与「机辅人定」的对外口径一致。** 机器给的和人定的各在各的列里，
   这本身就是这套框架最好的现场演示。

**渲染分两处，不一样：**

- **页面④（屏幕）**：12 家已经要横向滚动，再翻一倍列数不可用。
  因此改判在**单元格内**用第二行小字呈现（`2.6` 下方 `人工 2.9`），合计行同理出两行。
- **导出报告（纵向文档，不受屏宽限制）**：用真正的并排两列，
  「系统判分 / 专家判分」，并在末尾单列一节 `expert_reviews` 全表。

**未评定项被专家改判后仍然是未评定**：`matrix[].scores` 保持 `null`、页面④仍显示 `—`、
`totals[].score` 仍不计入，只有 `expert_score` 计入。系统没判出来这件事不因为人补了分而消失。
