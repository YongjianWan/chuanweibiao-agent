# 智能体工厂端点接入实测（B2 的解除依据）

> 实测日期：2026-08-20。端点 `http://192.168.102.104:5023`，智能体 `agent-14748c8d`。
> 本文只记**我方实测到的事实与代码上的应对**，平台通用坑另见公司内部《智能体工厂-接入避坑指南》。
> 凡与该指南冲突之处，以本文的实测为准并已注明。
>
> **术语**：本文的「端点」指上述智能体工厂对话接口；「S3」指本项目的逐项评审阶段（README §3）。
> 「228 次调用」= 12 家投标人 × 19 个评分项，是本项目跑一轮的规模。

---

## 1. 结论先行

**可以用它解除 B2，性能远好于原推算，但有一处交付口径要改。**

| 指标 | 实测值（清理 agent 人格后，见 §3.1） | 对照 |
|---|---|---|
| 单次调用耗时 | 中位 **1.6 秒**（1.1~6.8 秒，n=55） | README §6 阶段二原推算 8 秒，且注明「无任何依据」 |
| 1 家 19 项端到端 | **29~42 秒**（串行，不并发） | 清理人格前为 73 秒 |
| 12 家外推 | **约 7.5 分钟** | 预算 50 分钟，富余约 6.7 倍 |
| 未评定项 | **0 / 57** | §6 阶段二完成判定要求为 0 |
| 重试率 | **7.9%**（累计 76 次调用中 6 次），228 次外推约 18 次、退避约 36 秒 | 清理人格前 5.6%，**无改善**，见 §3.1。单批波动大，见 §3.3 |
| token 计数 | **拿不到**，`usage` 恒为 `null` | **未满足 B2 原定解除条件**，见第 4 节 |

样本：3 家 × 19 项 = 57 项（中冶建工、济南一建、山东三箭），2 项未命中故实际调用 55 次。

**由此，「并发路数够不够」不再是阶段二的风险点。** 原先整节算力账建立在「每次 8 秒、
需并发 8 路」的推算上，实测表明串行即达标。T9 的重点相应收窄为：连续 228 次调用下端点是否稳定。

复现（先按 README §10.1 重建 S1/S2 产物）：

```bash

export AF_AGENT_ID="agent-14748c8d"
export AF_API_KEY="<密钥，只走环境变量，不写进文件>"
B="中冶建工集团有限公司8010856"
```

## 2. 五处必须处理的差异（已在 `src/s3_review.py` 的 `AgentFactoryClient` 落地）

### 2.1 不传 `thread_id` **并非**每次独立 —— 最危险的一条

**平台文档写的是「不传每次独立」，实测为错。**

```
调用 1（不传 thread_id）：「请记住这个暗号：紫色犀牛7391」  → 「记住了」
调用 2（不传 thread_id）：「我刚才让你记住的暗号是什么？」  → 「紫色犀牛7391。」
调用 3（传新 thread_id）：「暗号是什么？」                  → 「我不知道暗号是什么。」
```

**后果**：228 次评审若不传 `thread_id`，各家标书内容会互相污染——第 12 家的判分能看到前 11 家的
证据。这撞 README §0 已定的边界「只做每家独立打分」，且会让同一份标书两次跑出不同结果，
现场被问「重跑一遍一样吗」时无法回答。

**应对**：每次调用传本进程内唯一的 `thread_id`，格式 `{run_id}-{四位序号}`，
序号自增并加锁（并发安全）。**重跑换新 `run_id`**，不复用历史会话。
守护测试：`tests/test_s3_review.py::test_agent_factory_thread_ids_are_unique_under_concurrency`。

**副作用（尚未处理，见第 5 节）**：一轮跑完会在平台上留下 228 个会话，
每个会话结束后自动写记忆文件到 MinIO。

### 2.2 没有 system role

请求体只有一个 `message` 字符串。S3 的 system prompt（防幻觉约束、输出格式约束）
只能与 user 内容拼成一条发送。实现：`"\n\n".join(m["content"] for m in messages)`。

**这意味着 system 约束的强制力弱于 OpenAI 格式的端点**，是第 2.4 条偶发格式错的原因之一。

### 2.3 必须绕过 HTTP 代理，否则「看起来像端点挂了」

端点是内网地址，而 `urllib` 与 `curl` 都默认读 `HTTP_PROXY` 环境变量。
本机 `HTTP_PROXY=http://127.0.0.1:7897`，走代理访问内网直接超时，且**返回 `code=000` 不带任何错误信息**——
排查时极易误判成端点宕机。实测中根路径、sessions、memory 三个端点全部 `000`，
而同时用原始 socket 发 HTTP 请求，nginx 9 毫秒就返回了 200。

**应对**：`urllib.request.build_opener(urllib.request.ProxyHandler({}))`，
命令行用 `curl --noproxy '*'`。

### 2.4 输出不保证是合法 JSON

19 项实测中 1 项（约 5%）在 JSON 前吐了一段英文思考过程并把 JSON 裹进 ``` 代码块；
另一轮 3 次探针中有 1 次（33%）如此。**原 `_parse_json_object()` 只处理「整段以 ``` 开头」的情形**，
围栏前有文字时直接解析失败。

**应对**：解析降级三步——剥 `</think>` 之后的正文 → 剥 ``` 围栏 →
**抠出第一个花括号平衡的 JSON 对象**（跳过字符串内的括号与转义，否则 `reason` 里出现 `}` 会截错位置）。
守护测试：`test_parse_json_object_survives_prose_and_fences`。

### 2.5 `temperature` 不可控

端点不接受该参数。同一证据包三次调用判分为 3.6 / 3.7 / 3.5，**档位一致（均为「优」）**。

按 README §1 的 P0 口径（档位不能错，档位内差异可接受）这是可接受的，
但**报告里不得声称结果逐位可复现**。

## 3. 实测结果质量

### 3.1 清理 agent 人格的效果：不治格式错，但提速 2.5 倍

该 agent 初始人格自称「窜围标智能体」，`SOUL.md` 只有半句话，输出里夹带自我介绍、
能力边界声明、读取工作目录文件的独白（见 §6 的 P2 复现）。2026-08-20 已改写为
「技术标辅助评审」并加入六条行为约束（不输出推理过程、不寒暄、不评论任务性质、
指令要求 JSON 时只输出 JSON 本身等）。

**同一家（中冶建工）同样 19 项，前后对比：**

| | 端到端 | 单次中位 | `out_tokens`（估算） | 重试率 |
|---|---|---|---|---|
| 清理前 | 70.3 秒 | 3471 ms | 14,713 | 5.6%（18 项中 1 次） |
| 清理后 | 28.1 秒 | 1538 ms | 2,865 | 0%（18 项中 0 次） |

**结论分两半，别只记住好的那半：**

- **提速是真的，且原因明确**：`out_tokens` 降到原来的 1/5——它不再输出废话，
  生成量少了，耗时自然降。这是清理人格最实在的收益。
- **格式错误率没有改善**：扩到 3 家 55 次调用，重试率 5.5%，与清理前的 5.6% 持平。
  **那几个百分点是模型偶发，不是人格干扰**，只能靠 README §3.6 的重试兜底。
  原先「清理人格也许能治格式错」的假设，实测不成立。

**档位分布的变化不可归因**：清理前后单家分布确有差异（优 14/良 2/一般 2 → 优 12/良 5/一般 1），
但单家样本仅 19 项，且该端点 `temperature` 不可控（§2.5），
这点差异无法区分是人格改动还是随机波动。不要拿它论证判分质量变好。

### 3.3 重试率的波动比预想大，不要拿单批数字对外承诺

逐批实测（同一端点、同一 prompt，仅模型随机性不同）：

| 批次 | 有调用项数 | 重试次数 | 该批重试率 |
|---|---|---|---|
| 清理人格前 · 中冶建工 | 18 | 1 | 5.6% |
| 清理人格后 · 中冶建工 | 18 | 0 | 0% |
| 清理人格后 · 另 2 家 | 37 | 3 | 8.1% |
| 解析增强后 · 中冶建工重跑 | 18 | 3 | 16.7% |
| **累计** | **91** | **7** | **7.7%** |

同一家同样 19 项，重试次数在 0~3 之间跳。**单批样本不足以定口径**，
报告里若要给这个数，等 8/21 全量 228 次跑完再取。

耗时随之波动：同一家 28 秒 / 49 秒，差的正是 3 次重试及其 2 秒退避。
**即便按最差的 16.7% 外推，228 次约 38 次重试、退避约 76 秒，仍不影响 50 分钟预算。**

## 3.4 解析降级策略（为什么只做零损失的那几级）

模型输出不保证是合法 JSON（§2.4）。`src/s3_review.py` 的 `_parse_json_object()`
按**数据损失从小到大**分四级降级，全部零损失：

| 级 | 做什么 | 损失 |
|---|---|---|
| 1 | 剥 `</think>` 之后的正文、剥 ``` 代码块围栏 | 零 |
| 2 | 直接 `json.loads` | 零 |
| 3 | `_repair_json`：中文顿号 → 逗号；`_balance_json` 补全缺失的 `}` `]` | 零，只补不删 |
| 4 | 抠出第一个花括号平衡的对象再解析（必要时再修一次） | 零，只削外围噪声 |

思路取自「可信空间数据产品」前端 `js/app.js` 的 `parseJSON()` / `balanceJson()`，
那是 2026-07 联调实测出来的。**但刻意少做两件它做了的事：**

- **不做「逐段砍尾」**：该前端第五级会从末尾一个个砍掉不完整片段直到能解析。
  它砍掉的是产品卡片，页面少显示一张可以接受；本项目的评审结果只有
  `tier` / `score` / `cite` / `reason` 四个字段，砍掉任一个都是判分失效。
  更危险的是 `{"tier":"优","score":` 砍尾后变成 `{"tier":"优"}` ——
  **合法但没有分数**，会一路通过解析。
- **不补未闭合的字符串**：断在 `reason` 中间时补个引号即可让 JSON 合法，
  代价是一条半句话的判分理由，且它会**静默通过** `_validate_model_output()`。

两条是同一个判断：**有重试的系统宁可失败重来，没重试的系统才需要有损抢救。**
该前端没有重试、用户在页面上等着；本项目有 README §3.6 的重试，重来只花 2 秒。
行为由 `tests/test_s3_review.py` 的四条断言锁住，改之前先看那几条的注释。

### 3.2 判分内容质量（首轮 1 家 19 项）

档位分布：优 14 / 良 2 / 一般 2 / 未命中 1（T-01，`miss_reason: not_found`，即 #11 的误杀之一）。

`reason` 字段质量达到交付要求——具体引用了证据编号、写明了差在哪、含针对本项目的判断。例（T-02）：

> 投标文件系统编制了进度管理方案……明确承诺 1020 日历天总工期与招标文件一致……
> 将总工期层层分解、设置关键线路节点工期……

**档位明显偏松（19 项判优 14 项）**，属 README §6 阶段三「分数校准」范畴，本次测试不做，
但需在报告中说明。若 12 家都是这个分布，S4 的 `audit` 字段（某项全家同档）会大面积触发。

## 4. 一处交付口径必须改：token 计数拿不到

响应的 `usage` 字段恒为 `null`。而 README §1 把性能数据列为 P0——
客户第一轮收到的竞品报告里就只有性能数据。

**应对**：`AgentFactoryClient._estimate_tokens()` 按中文约 1.5 字/token 本地估算，
上例得 `in_tokens: 56736 / out_tokens: 14713`（1 家 19 项）。

**这是估算不是实测，交付报告中必须标注来源，不得与端点返回的真实计数混列。**
`docs/data-contract.md` 报告数据的 `compute_notes` 应增写一条说明；口径待拍板，
已登记在 `docs/issues.md`。
