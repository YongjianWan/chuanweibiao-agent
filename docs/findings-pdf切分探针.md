# 探针结论：真实投标 PDF 用什么切块

> 日期：2026-08-19
> 目的：为 S1 的 PDF 切分策略定案（`docs/issues.md` 的 P0）。
> 方法：对 12 家 × 19 个技术标 PDF（共 228 个、40.5 万行）统计结构信号。
> 复现：`python scripts/probe_pdf_structure.py`（抽样三份的详细统计）。
> 本文所有数字均为该批真实文件的实测值。

## 一、结论先行

**切分规则 = 编号模式定层级 + 相对满行宽区分标题与正文。字号和加粗信号完全不可用。**

层级由编号类型直接给出：

| 层级 | 编号形式 | 例 |
|---|---|---|
| 1 | `第N章` / `第N节` | 第二章、施工组织总体设想和部署 |
| 2 | 中文数字 + `、` | 一、工程概况 |
| 3 | `N、` / `N.` | 1、编制说明 |
| 4 | `N.N` / `N.N.N` | 2.6.1、国家规范、标准 |
| 5 | `（N）` / `（一）` | （1）给水系统工艺流程 |

**标题判定：该行匹配上表任一编号形式，且行长 < 0.8 × 本文档的满行宽度。**
满行宽度取该文档全部行长的 P90。**这是相对量，随文档自适应，不是绝对字数阈值**
（CLAUDE.md 的「魔数要归零」）。

## 二、为什么字号和加粗用不了

抽查三份不同投标人、不同评分项的 PDF：

| 文件 | 行数 | 字号分布 | 加粗行 |
|---|---|---|---|
| 中冶建工 · 施工方案及技术措施 | 4,181 | **12.0pt 占 100%** | **0 (0.0%)** |
| 中建五局 · 进度管理方案 | 1,898 | **12.0pt 占 100%** | **0 (0.0%)** |
| 济南一建 · 服务采购管理方案 | 178 | **12.0pt 占 100%** | **0 (0.0%)** |

**投标系统在生成 PDF 时把所有字体格式抹平了**，全文单一字号、无加粗。
因此「按字号/加粗推断标题」这条路直接排除，不需要再试。
加上此前已确认的 `get_toc()` 返回空（无书签），**编号模式是唯一剩下的结构信号**。

## 三、为什么标题判定要用「相对满行宽」而不是绝对字数

编号本身不足以区分标题和正文——正文里大量段落也以编号开头：

```
标题： 1.1工程概况简述
正文： 1.1、采用分段流水施工作业，确保重点分项工程和关键工序的施工进度，根据本工
标题： 2.6.1、国家规范、标准
正文： 2.2.1、木模板拼缝处应平直刨光，拼板紧密；浇混凝土前要隔液浇水，使模板润湿
```

**区分它们的是行长**：PyMuPDF 的「行」是视觉换行，正文段落被硬折到满行宽，
所以正文的首行几乎总是顶到满行；标题提前结束，明显短。

实测印证：中建五局那份的行长中位数与 P75 都是 36，即绝大多数行是满行——
这正是硬折行的特征。而各文档的满行宽度并不相同（实测 37~38 字不等），
所以阈值必须相对于每份文档自己的 P90 行长，不能写死。

各编号形式在「短于中位数」上的表现（中冶建工那份）：

| 编号形式 | 出现行数 | 其中短行占比 | 判读 |
|---|---|---|---|
| 第N章/节 | 5 | 100% | 极可靠，全是真标题 |
| 中文数字、 | 35 | 100% | 极可靠 |
| N、/N. | 163 | 88% | 可靠 |
| N.N | 583 | 63% | 需行长过滤 |
| N.N.N | 284 | 49% | 需行长过滤 |
| （N） | 398 | 32% | 最需要行长过滤 |

越深的编号越容易出现在正文里，越依赖行长过滤——这与直觉一致。

## 四、切出来的粒度

对全部 228 个 PDF 应用上述规则：

| 指标 | 实测值 | 对照 |
|---|---|---|
| 每个 PDF 切出的章节块数 | 中位 111 | — |
| 章节块字数 | 中位 114 字，P10 23，P90 292 | docx 路径为中位 301 字 |
| 识别为标题的行占全部行 | 16.0%（64,783 / 405,254） | — |

**粒度与 docx 路径同量级，S2 现有的检索算法可以直接用，不需要改。**

## 五、碎块问题，以及它为什么不用单独处理

分布两头都有极端：

- 最碎：`济南一建 · 施工总进度计划及保证措施`，块字数中位数 **4 字**——
  该文件主体是进度表格，每个单元格自成一行且以数字开头，被全判成标题。
- 最粗：`中冶建工 · 服务采购管理方案`，块字数中位数 **1807 字**，全文只识别出 4 个标题。

**这不需要额外的合并逻辑，§3.3 已有的「证据按直接父章节整段收取」会吸收掉。**
碎块在检索时各自打分，收取时连同其直接父章节的全部兄弟块一起收，自然成段。

**反过来验证了 §3.3 当初为什么选「直接父章节」而不是「固定第 N 级标题」。**
本次实测了固定层级聚合（把层级 1、2 作为单元边界）的效果：

| 指标 | 固定层级 1~2 聚合 |
|---|---|
| 单元字数中位数 | 中位 1723，**P90 23,003，最大 278,553** |

P90 就已经是 budget（3000 字）的 7.7 倍，最大的那份直接把整个 PDF 变成一个单元——
因为那份文档根本没有 `第N章` 或 `中文数字、` 层级的标题。
**固定层级在这批文件上彻底失效，直接父章节自适应，这条设计不用动。**

## 六、对现有契约的影响

| 契约字段 | 结论 |
|---|---|
| §4 章节块 `level` | 取上表的 1~5，由编号形式决定 |
| §4 章节块 `path` | 由各级标题文本累积而成，与 docx 路径同构 |
| §4 章节块 `id` | 格式不变，`文件序号#章节序号` |
| §4 章节块 `item_guid` | 取自文件名尾部 GUID，见 §2.1 |
| §3.3 父章节整段收取 | **不变**，本次实测反而加强了它的依据 |
| §5.3 页面⑤「在原文中定位」 | 按 `id` 定位到块，块内带页码可跳转 PDF 页 |
| `src/s2_locate.py` | **不需要改**，粒度与 docx 路径同量级 |

## 七、未验证的部分

- 表格内容（进度横道图、资源配置表）当前被当成普通文本行处理，
  切出来是碎块。是否需要专门识别表格并整体保留，本次未测。
  影响面：`施工总进度计划及保证措施` 这类以表格为主的评分项。
- 页眉页脚是否混入正文，本次未单独剔除。docx 路径没有这个问题。
- 上述规则在**换一个项目**的 PDF 上是否成立，未验证。
  本批 228 个 PDF 出自同一投标系统，格式高度一致。
