## 1. 分工原则

**三个人的盘子里，能合并的模块必须合并。**

- **S4 报告不设独立模块，并入前端。** 报告的数据层是 `README.md` §4 已冻结的
  「报告数据」JSON，渲染层就是页面④加上性能数据。让前端顺手导出静态 HTML，
  比后端另写一个渲染模块省一整个人天。
- **性能埋点不设独立任务，写进 S3 的调用封装。** 每次调用的 token 与耗时落盘，
  是 S3 本来就要做的事。

**角色先于技能。** 分工按**角色**划，不按谁会什么划——
Aiden 是项目经理，即使他会写算法，也不该承担实现任务：
他一旦陷进某个模块，B2/B3/B5 三个阻塞项就没人追，而那三件事没有任何人能替。
（过去这份文档把 T1/T2/T7/T9 四个任务都挂在 Aiden 名下，是按技能排的，已纠正。
README §7 的角色列与开头那句「Aiden（算法 + 清障）」需同步改，见 §6。）

| 线     | 角色定位                                   | 负责                                                          | 卡什么                                          |
| ------ | ------------------------------------------ | ------------------------------------------------------------- | ----------------------------------------------- |
| Aiden  | **项目经理**：清障、决策、验收、对外 | B2/B3/B5 清障；T1/T7 业务配置；逐项验收；对客户与陈老板的口径 | 不卡别人，但 B2 卡所有人                        |
| 后端   | 实现                                       | 数据管道 T0 → T8 → T3                                       | 不卡。切分策略已定案（README §3.7）            |
| 模型侧 | 实现                                       | T2 + T9                                                       | B2。新人 8/19 入场、8/20 起产出，有效工时仅一天 |
| 前端   | 实现                                       | 界面与报告 T5 → T6 → 报告导出；造 mock（§2）               | 不卡。只依赖 README §4 的数据契约              |

**Aiden 承担 T1 与 T7 不违反上面这条**，因为这两项是**业务配置不是实现**：
T1 是读招标文件拆出 19 项的分值、档位与要素权重，T7 是据此填检索词与同义词。
它们要的是对招标文件和评标口径的理解，不是写代码，且 README §1.1 已明确
「离线产出、允许人 + AI 协作、不要求全自动」。**Aiden 的产出物是核对签字过的 yaml，
不是代码。**

**真实的关键路径是一条串行链，它串起全部实现线：**

```
T0 ──→ T8 ──→ T2 ──→ 全量演练 ──→ 交付
（后端）  （后端）（模型侧）  （全员）
                ↑
                B2（外部，唯一不可控项 · Aiden 清障）
```

前端的 T5/T6 可以并行推进（靠 §2 的 mock 顶着），但**最终交付物必须走完这条串行链**。
过去把两条线描述成「互不阻塞」掩盖了这一段——它们在 T2 交汇，而交汇点原本排在交付当天。
§4 的排期把交汇提前到 8/20 晚，就是为了给全量演练腾出时间。

## 2. 测试数据用真的，只有一处例外

**S1、S2 的中间产物一律跑真实文件，不手写假数据。**

真实文件已在 `原始资料/实际测试工程文件/` 下（12 家、241 个 PDF）。
后端 T0 完成后，`data/interim/sections.json` 与 `located.json` 即为真实数据，
前端直接读。手写的假 JSON 一定和真实输出对不上（字段缺失、路径杜撰、字数不真实），
照它做完还要返工一次。

**唯一的例外是 S3 的输出 `review_results.json`。**

原因有两条：

1. **物理上不存在**——B2 未解除，模型一次都调不了。前端的页面④⑤要显示判分、理由、
   置信度、`unrated` 与 `⚠` 标记，这些只能来自 S3。
2. **部分状态真跑也难凑**——`unrated`（需模型连续失败三次）、`confidence < 0.85`
   （README §4 的阈值，走了降级检索或两个减分因素叠加才触发）、某评分项 12 家全部未命中。
   这些边界态前端必须做对（`0` 与 `—` 混淆会误导评标，见 `docs/ui-spec.md` 页面④），
   但正常跑一遍未必碰得到，本来就该构造。

**谁造：前端自己造。** 用它的人最清楚需要哪些边界态，转手一道反而失真。
**什么时候造：8/19 内**，不等后端的真实数据。

**构造方式：照着一份真实的 `located.json` 生成，不凭空编。**
`bidder`、`item_id`、`item_guid`、`cite` 的编号范围、证据文件名全部取自证据包，
只有 `score` / `tier` / `reason` / `confidence` 是编的。
额外塞入三条边界态：一条 `unrated`（`score` 必须为 null 不是 0）、
一条 `confidence < 0.85`、一项全家未命中。

**8/19 当天用哪份 `located.json` 打底**：T0 还没完成，用早期软件标样例产出的那份
（`原始资料/公司的临时样例文件仅作参考/`，结构正确、内容不对，见 `docs/findings-原始资料缺陷.md` 第 4 条）。
**结构对了就够**——mock 要的是字段齐全和边界态，不是内容真实。
T8 产出带 `bidder` / `item_id` 的真实证据包后（8/20 中午），前端把 mock 重新生成一次。

产出位置 `data/interim/mock/review_results.json`。**B2 解除、T2 跑通后立即删除。**

## 5. 落后了砍什么（按此顺序）

**若 §0 前提一成立（8/21 不可推迟），这一节不是保险，是主计划——
砍不砍要在 8/20 中午决定，不能等 8/21 演练崩了再砍。**

**若 §0 前提二选了 C（不加人），砍单提前到 8/19 下班决定**——
3 个人两天半排不下当前的量，越晚砍，已经写下去的工时越是白费。

1. **页面⑤的原文定位跳转**——能显示引用原文即可，跳转高亮是加分项。
   （T0 的页码字段仍然要写，成本为零，砍的只是前端跳转。）
2. **页面④的「疑似映射问题」整行标记**——它是审计信号，不是交付物。
3. **页面②的「打开对照」跳转**——人工核对时手动翻招标文件也能核。
4. **断点续跑的自动扫描**（只砍后半，逐项落盘必须留，见下）。

三样全砍掉，仍然满足 README §1 的两条 P0：真实跑完、判分有原文出处可查。

**从可砍列表里移出去的两项：**

- **要素加权定分**：已于 2026-08-19 晚**直接砍掉**，不再是候选项。
  `score` 由模型在档位区间内直接给出，`factor_scores` 字段与页面⑤的「区间内定分」块删除。
  要素分解的检索侧用途保留，降级为不带权的 `aspects`（T1 产出、T7 补同义词、T8 消费）。
  见 `docs/data-contract.md` 的「为什么不做要素加权定分」。
- **断点续跑**：**拆两半，前半不可砍、后半可退化**。
  它不是"挂了重跑也就 50 分钟"——README §6 阶段二的**完成判定原文就写着**
  「中途杀进程后能从断点续跑」，它是验收标准的一部分；且跑到第 9 家崩了从头再来
  就直接撞穿 50 分钟这条 P0，客户现场盯着，没有第二次机会。
  - **① S3 结果逐项落盘 —— 不可砍。** 成本接近零，就是别攒在内存里最后一次性写。
  - **② 启动时自动扫描已完成项、跳过并重排并发槽 —— 落后了可退化**为当天手工指定
    从第几家继续。
  整体按**半天**估，不是半小时：并发调度要处理「已完成项不占并发槽」，
  还要和 README §3.6 那轮「全跑完后统一重跑 unrated」对齐。

**不能砍的：**

- 页面③的实时滚动——P0「不作弊」的唯一可见证据。
- 未评定（`—`）与 0 分的区分——混淆会误导评标。
- 每个判分的原文引用——P1 考核项。
- **8/21 上午的全量演练**——这不是开发任务，是验收动作本身。
  砍掉它等于把第一次全量运行放在客户面前，那是 P0「真实跑完」的最大风险来源。
