## 0. 一句话

起一个服务，浏览器点四下，**全程约 6 分钟**（2026-08-20 深夜实测 345.6 秒，
含 S1 入库到出报告的全程），客户全程可见。

## 1. 开演前 10 分钟（自己做，不给客户看）

### 1.1 探活——**这步不能跳**

```bash
source config/af-endpoint.sh && python scripts/ping_endpoint.py
```

- 输出 `✓ 端点可用` → 继续下一步
- 输出 `✗ 端点不可用` → **不要开演**。报错是 `Agent 'agent-xxx' not initialized.` 的话，
  **重启 agent** 即可（2026-08-21 凌晨验证过：重启后立刻恢复正常），重启完再跑一次这条命令确认

为什么不能跳：2026-08-20 深夜真跑过一次端点没起的情况，**228 项全部未评定**，
而跑完一整轮才发现，白花 7 分钟。这条命令 10 秒给结论。

**这个端点会反复进入「未初始化」状态**——当晚观察到至少两次，一次在 12 路并发之后，
一次在空闲一段时间之后，都靠重启 agent 恢复。所以：开演前必 ping；演示中途大面积
未评定时立刻 ping。

### 1.2 用 Mock 排练一遍界面

```bash
python src/server.py --mock --clean
```

浏览器开 <http://127.0.0.1:8000/>，按第 2 节的四步走一遍。**约 30 秒跑完**，
不调用真实端点、不花额度。确认界面顺、没报错，然后回终端 `Ctrl-C` 停掉。

> `--clean` 会清空 `data/runs/`（历次运行的产物）。排练完清干净，正式演示的目录才清爽。

### 1.3 起正式服务

```bash
source config/af-endpoint.sh && python src/server.py
```

终端会打印：

```
服务已启动：http://127.0.0.1:8000/    模式：真实端点（需 AF_BASE_URL / AF_AGENT_ID / AF_API_KEY）
投标文件目录：...\济阳区实验高级中学项目工程总承包（EPC） 2
  存在
```

**必须看到「存在」**。显示「不存在」说明原始资料目录被移动过，页面①点下一步会报错。

浏览器开 <http://127.0.0.1:8000/>，停在页面①，等客户到齐。

## 2. 正式演示（四步）

### 第一步：页面① 选投标文件

点「**选择投标文件**」，选**文件夹**（不是选文件）：投标文件目录。

界面应显示：

- 右上角 `12/12 已识别`
- 每家一行：`20 个技术标 PDF / 16.2 MB / 19/19 项文件名匹配`

**这一步是给客户看的**：我们读的就是这批文件，每个评分项都对上了对应的 PDF。
（对应关系是文件名尾部的 GUID，README §2.1）

> 如果显示不是 12/12：选错目录了，重选。

### 第二步：点「下一步：解析」——**计时从这一刻开始**

按下去之后：

- 页面跳到②，右上角计时器开始走
- **后台已经在真跑 S1（PDF 切块）和 S2（证据定位）**，约 30 秒

客户可能问「为什么还没确认就开始解析了」——照实说：**投标文件的处理必须计入总耗时**，
所以从点这个按钮就开始计时、开始跑；而**打分那一步要等你确认评分标准之后才会开始**。

### 第三步：页面② 核对评分标准，然后点「开始评审」

这一页展示 19 个评分项、分值、三档区间、以及每项的招标文件原文（点「查看招标原文」）。

**这是全流程唯一的人工介入点**，也是展示「评分表是从招标文件抽出来的、当场可核」的位置。
慢慢讲没关系，后台在跑 S1/S2。

核对完点「**开始评审**」。S3 从这一刻才开始：228 项（12 家 × 19 项）、并发 4 路、
**约 5 分钟**。

**各阶段该等多久**（2026-08-20 深夜实测，按文件落盘时间戳统计）：

| 阶段 | 耗时 | 页面③的表现 |
|---|---|---|
| S1 入库（12 家 240 个 PDF） | 约 13 秒 | 「PDF入库」打勾 |
| 章节合并 | 约 1 秒 | 同上 |
| S2 证据定位 | 约 7 秒 | 「证据定位」打勾 |
| **S3 逐项评审** | **约 322 秒** | 逐项滚动，进度条 x/228 |
| S4 汇总报告 | 约 2 秒 | 「结果汇总」打勾 |
| **全程** | **345.6 秒（5.8 分钟）** | 从点「下一步：解析」到「评审完成」 |

所以点完「开始评审」之后，**前 20 秒页面③可能还在跑 S1/S2**（如果你在页面②停留时间短），
之后才开始逐项滚动。别以为卡住了。

> 按钮点不动（灰的）？说明文件名预检没通过（页面②「投标文件绑定」显示「待确认」）。
> 回页面①重选目录。

### 第四步：页面③ 看它跑

逐项实时滚动，每完成一项出现一行：投标人 · 评分项 · 档位 · 得分。
上方实时显示：进度 x/228、已用时间、当前并发、累计 token、重试次数、未评定数。

**客户盯的就是这一页。** 关于这页的两句准备好的话：

- 「暂停滚动」按钮**只停页面显示，后台的模型调用不会停，计时也照走**——按钮上写了，别说成"暂停运行"
- GPU/显存显示「未采集」是**故意的**：模型跑在远程端点上，我方进程内采集不到显存，不伪造数据

跑完后自动进入「评审完成」，四个阶段全部打勾。

### 第五步：页面④ 结果与导出

- 12 家 × 19 项矩阵，评分项列固定、可横向滚动
- 点任意分数进详情页：判分理由 + 引用的投标文件原文 + 章节出处
- 「**导出报告**」生成静态 HTML，含并排表、未评定单列、建议复核清单、性能数据、算力说明
- 「**导出 Excel**」生成 `评审报告.xlsx`，五个工作表。**第一张就是「判分与依据」**：
  228 行，每行是「得分 → 判分理由 → 依据出处」，出处写到
  `某某方案.pdf · p.15 · 第二章 设计质量保证措施 > 一、设计质量目标 > 1、…`，
  评委可以直接翻回投标文件那一页核对。后面才是评分汇总矩阵、未评定、建议复核、性能与算力。
  **甲方要表格给这个**，能筛选排序

> **交付时这么说**：本次给的不是一张分数表，是一张「每一分都能翻回原文」的对照表——
> 分数右边就是判分理由，理由右边就是这条理由依据的原文出处。分数准不准是第二阶段的事，
> 这一阶段保证的是每个判分都查得到出处。

> 命令行等价物（服务没起时也能生成）：
> `python scripts/export_xlsx.py data/runs/<run_id>/report/report.json`

## 3. 现场可能被问到的问题

| 客户问 | 怎么答 |
|---|---|
| 有一项显示「未评定」，是出错了吗？ | 不是 0 分、也不是故障：模型给的分数超出了该档位的区间，系统重试三次仍越界，就拒绝接受、标为未评定交人处理，而不是硬塞一个分数。实测 228 项里出现 0~1 项 |
| 这是提前跑好的吧？ | 现在跑的是本次点击产生的运行，`data/runs/` 下每次一个新目录。可以当场换一份文件重跑，页面内容会跟着变 |
| 为什么有些项标「建议复核」？ | 两种情况：**证据降级**（细粒度检索词没命中，退回用评分项名重检索，证据可能不对题），或某个评分项各家判成同一档、**区分不出来**。系统标出来交人复核，不替人拍板。本次实测复核项很少——检索词补齐后降级率是 0 |
| 显存多少？跑在什么卡上？ | 模型在远程端点上，我方进程采不到显存，报告里写「未采集」。算力归属是神思自有算力 |
| token 用了多少？ | 报告里有，但**必须说明是本地估算**——端点不返回 token 计数，按中文约 1.5 字/token 估的 |
| 分数准不准？ | 本次交付的是「可追溯的判分」：每个分数都能点开看依据的原文。分数与专家的一致性校准是第二阶段工作 |
| 能不能跨家对比、找出串标？ | 本次范围是每家独立打分，系统并排展示供人比较，不做跨家对比判断（README §0） |

## 4. 出问题怎么办

| 现象 | 处理 |
|---|---|
| 页面③大量「未评定」 | 立刻在终端跑 `python scripts/ping_endpoint.py`。**ping 也失败 = agent 未初始化**，重启 agent 后按下一行补跑；**ping 正常 = 并发压力**，降并发重来 |
| 少量「未评定」，想当场补上 | 端点正常后跑下面这条，**只重跑未评定的项，已判分的不动**（实测补 1 项约 14 秒）：<br>`python src/scheduler.py --evidence data/runs/<run_id>/evidence --scoring-table "config/projects/济阳区实验高级中学.yaml" --project-summary "config/projects/项目特征摘要.md" --sections data/runs/<run_id>/sections_all.json --output data/runs/<run_id>/reviews --concurrency 4 --agent-factory --retry-unrated`<br>补完再跑一次 S4 生成报告（命令见 README §10.1）。补跑耗时会**累加**进总耗时，不会覆盖 |
| 跑到一半进程崩了 | 断点续跑：原样重跑那条 scheduler 命令，已完成的项不会重跑。命令见 README §10.1 |
| 页面③一直不滚 | 看终端有没有报错。确认页面②的「开始评审」点过了——S3 要等这个确认 |
| 浏览器打不开页面 | 确认服务终端还开着、没被 Ctrl-C。端口默认 8000，被占用就 `--port 8080` |
| 服务中途崩了、重启后页面④空了 | 重启服务后，用崩之前那次的 `run_id` 仍能取报告（服务会回退到磁盘上的 `data/runs/<run_id>/`）。实在不行直接用命令行导出 Excel 给客户 |
| 想重来一遍 | 刷新页面回页面①，或点页面③底部「重置流程」。每次点「下一步：解析」都是全新运行 |

**兜底方案**：服务层起不来时，直接用浏览器打开 `prototype/index.html` 也能演示界面，
但那是**上一次运行的回放**，页面③会自己说明这一点。
真到这一步，**必须主动告诉客户这是回放**，不要让客户自己发现。

## 5. 演示后

产物在 `data/runs/<run_id>/`：

- `sections/`、`sections_all.json` —— S1 切出的章节块
- `evidence/` —— S2 定位的证据包
- `reviews/reviews.json` —— S3 的 228 条判分（含每项的 attempts、耗时）
- `report/report.json` 与同目录 markdown —— S4 报告

这些**不进 git**（含评审分数，`.gitignore` 已挡）。需要留档就自己复制走。
