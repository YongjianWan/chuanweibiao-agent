## 0. 一句话

**输入** 一份招标文件 + 多份投标文件（同一个工程建设项目的多家投标人），
**输出** 每家在每个评分项上的得分、判分理由、以及理由所依据的投标文件原文出处，
外加一份性能数据（耗时、token 量，显存若可采集则一并给出）。

本次实测项目为**济阳区实验高级中学工程总承包（EPC）**，**12 家投标人**，
技术标 19 个评分项、满分 100 分。（依据：实测，见 `docs/findings-招标文件核对.md`）

**这不是串标围标识别系统。** 项目目录名叫「串围标智能体」，但本次交付的实际内容是
上面描述的技术标辅助评审打分。串标围标识别（多家标书雷同比对、报价异常规律）不在本次范围内。
这个命名冲突尚未在组织层面澄清，见 §8 的 B4。

**已定的边界：只做每家独立打分，不做跨家对比评审。**
系统对每家分别评分，页面④把结果并排展示供人比较，但系统本身不产出「A 比 B 好在哪」这类判断。
（2026-08-18 决策。提出过增加一道跨家对比调用，已明确不做，不要再往这个方向加。）

## 1. 背景：这次到底在考什么

济南公共资源交易中心组织 AI 辅助评标测试。此前已有其他厂商完成第一轮，我方本次是争取到的第二次参与机会。
（依据：录音）

**关键认知：本次测试的主要考核项不是打分准不准，而是系统能否在可接受时间内真实跑完。**

依据（均来自录音）：客户第一轮收到的竞品测试报告中没有分数，只有性能数据（两轮各耗时多久、
跑在什么卡上、占用多大显存）；竞品成绩为一个项目 50 分钟；
客户表示会现场盯着跑，以确认不是预跑好结果当场播放。

**「50 分钟」按全部投标人计**（2026-08-19 决策），本次即 12 家。

**语料体量（依据：实测）**：本次项目 12 家技术标合计 **1047 万字**，
单家 29 万~226 万字，平均 87 万字。全部为 PDF，共 241 个文件（每家 20 个，含 1 个封面）。

体量数据来源为 `原始资料/实际测试工程文件/` 下的真实文件，用 PyMuPDF 抽取正文字数统计得到。
录音中提到的「客户实测一个项目 4000 万字量级」未在本项目得到印证，
可能指更大的项目或包含商务标；本文不再引用该数字。

因此考核项按优先级排列：

| 优先级 | 考核项 | 判定标准 |
|---|---|---|
| P0 | 真实跑完，不作弊 | 客户现场盯着跑，界面需实时反映进度，**不得预跑投标文件的评审结果**。评分表与要素属离线准备物，不在此限，界线见 §1.1 |
| P0 | 吞吐量 | **全部** 投标人标书总耗时 ≤ 50 分钟（越小越好）。本次为 12 家 / 228 次调用，约束等价于「单次耗时 ÷ 并发路数 ≤ 13.2 秒」 |
| P0 | 档位不能错 | 应得 5 分的项不能判成 8 分。档位内 1 分之差可接受 |
| P1 | 判分有据可查 | 每个判分必须给出投标文件原文引用及其章节出处 |
| P2 | 分数与专家一致 | 本次不追求。依据：2026-08-19 客户口径「先测一测就行，起码有个结果就行」。报告中正常给分，但交付的是**可追溯的判分**，分数校准是第二阶段。见 §6 阶段三 |

### 1.1 哪些能提前准备，哪些必须现场跑

这条界线在测试当天会被问到，先写清楚。（依据：2026-08-19 电话沟通）

**可以提前准备（离线产出，不计入 50 分钟）：**

- 从招标文件抽出的评分表：19 项、分值、三档区间
- 要素与二级要素及权重
- 项目特征摘要

理由：这三样只依赖招标文件。**招标文件是公开发布的，与任何一家投标文件无关**，
提前处理它不构成对评审结果的预知。竞品同样是在测试之前自己拆好的。
产出物落在 `config/projects/<项目名>.yaml`，测试当天直接读。

**必须现场跑（计入 50 分钟）：**

- S1 投标文件入库、S2 证据定位、S3 逐项评审、S4 汇总出报告

**计时起点：投标文件上传完成后、点下页面①的「下一步：解析」那一刻。**
不是页面③出现的时候——页面①点完就开跑 S1，S1 属于现场处理投标文件，必须计入。
因此**页面①点完「下一步：解析」就要显示计时器**，一直延续到页面③、④。

这个数当天一定会被问，先定死。好消息是 S1 很便宜：**实测 240 个 PDF、1047 万字，
单线程抽取加切分 39.4 秒，占 50 分钟预算的 1.3%**（复现：`python src/s1_ingest.py "原始资料/实际测试工程文件/济阳区实验高级中学项目工程总承包（EPC） 2" <输出路径>`）。
所以起点定得保守一些不影响达标。

**这就是作弊的界线**：预先跑出投标文件的评审结果、当场播放，是作弊；
提前准备评分规则，不是。§1 表中 P0「真实跑完，不作弊」针对的是前者。

因此 §5.3 页面③的实时滚动只需覆盖 S1~S4；页面②确认的是已准备好的评分表，
人工在此核对，不是当场生成。

## 2. 术语表

本文档内所有专有名词在此定义。文档正文不使用未在此定义的缩写或代号。

| 术语 | 定义 |
|---|---|
| **招标文件** | 甲方（招标人）发布的文件。其中含「评标办法」章节，规定每个评分项多少分、什么情况得几分。本系统评分规则的唯一来源。 |
| **投标文件** | 投标人提交的应答文件。本次只处理其中的**技术部分**，商务部分明确不处理。（依据：录音）**实际到手的技术标全部是 PDF**，每家 20 个文件、文件名与评分项一一对应，见 §2.1。（依据：实测） |
| **福莱通** | 完成本次测试第一轮的另一家厂商。其产出的 `拆分评审项.xlsx`（评分项拆成要素与权重）在开发期作为对照参考，**不进入本系统流程**，我方要素自建，见 §4 评分表 `factors`。 |
| **投标人 / bidder** | 参与同一个项目投标的一家单位。本次实测项目有 **12 家**。系统对每家分别跑一遍 S1/S2/S3。**`bidder` 的取值 = 投标文件所在的一级目录名原样照抄**，例 `中冶建工集团有限公司8010856`（尾部数字是投标系统给的投标编号，一并保留）。它是 §4 报告数据里 `matrix` 与 `totals` 的键，12 家写法必须一致，不得截断或改写。 |
| **评分项** | 招标文件评标办法里的一条打分条目，例如「施工方案及技术措施，8 分」。**评分的唯一依据。** 本次共 19 项，合计 100 分。 |
| **档位** | 一个评分项内部的分数梯度。本项目招标文件对全部 19 项统一采用**三档**：一般 / 良 / 优，每档给一个**分数区间**而非单一分值，例如「施工方案及技术措施」为 1-3 分 / 3-6 分 / 6-8 分。（依据：实测） |
| **项目特征摘要** | S0 从招标文件中抽出的 300~500 字概述：工程类型、规模、地质水文条件、招标文件点名的重难点。**注入每一次 S3 调用**，是判断「针对性」这一评分维度的前提。见 §3.4。 |
| **评审点** | 本系统预置的能力清单条目，共 114 条，来自甲方提供的 `评审点.md`。**它不是评分规则**，只提供该主题的检索关键词。**本项目用不上**——评分项与投标文件由 GUID 直接绑定（§2.1），不需要评审点做中介。是否保留见 `docs/issues.md` P2。 |
| **映射** | 把招标文件的「评分项」对应到系统的「评审点」以取得检索关键词，一个项目一份配置。**本项目不需要映射**——评分项与投标文件由 GUID 直接绑定（§2.1）。该词只在讨论换项目时的降级路径时出现。 |
| **GUID 绑定** | 评分项与投标 PDF 通过文件名尾部的 GUID 一一对应，见 §2.1。本项目最重要的结构事实。 |
| **得分率** | 一个要素或二级要素的完成程度，取值 0~1，越大越好。各级按权重加权后决定分数落在档位区间内的什么位置，见 §4 评审结果 `factor_scores`。 |
| **要素 / 二级要素** | 一个评分项内部的评分维度分解，两级，各级权重和为 1.0。例：「进度管理方案」拆成 4 个要素，每个要素再拆 3~4 个二级要素。**招标文件里没有这一层**，由我方从评分描述推导（2026-08-19 决策）。它同时是 S2 在单个文件内检索的粒度。 |
| **同义词扩展** | 为检索词补充标书实际会用的说法，例如要素描述写「S 曲线」而标书写「香蕉曲线」。检索不负责猜同义词，全靠这里补。见 §3.2 红线二。 |
| **章节块** | 投标文件切开后的最小单位，系统的检索和引用都以它为单位。docx 按 Word 标题层级切；PDF 按行首编号形式定层级、按相对满行宽区分标题与正文，见 §3.7。 |
| **证据单元** | 一个章节块的直接父章节及其下全部子块。S2 按证据单元整段收取，不收零散块。见 §3.2。 |
| **证据包** | 某个评分项在某家投标文件里检索定位到的若干证据单元，字数受 budget 约束。送给大模型的实际输入。 |
| **证据字数上限 / budget** | 单个证据包允许的最大字数，当前 3000 字。代码位置：`src/s2_locate.py` 的 `BUDGET`。**这是全系统的算力开关**：调大则精度升、耗时升。 |
| **锚点词** | 一组检索词中在本次语料里最罕见的那一个，代表该主题的领域特征。锚点词未出现在某章节块中，该块不作为证据候选。 |
| **DF / DF 占比** | 文档频率。一个词出现在多少个章节块里（DF），除以章节块总数即 DF 占比。占比越低区分度越高（越低越好）。系统用 DF 占比而非 IDF 绝对值设阈值，原因见 §3.2 红线一。 |
| **IDF** | 逆文档频率，由 DF 换算而来，用作打分权重。一个词越罕见 IDF 越高（越高越有区分度）。 |
| **压缩比** | **全部投标文件原文总字数 ÷ 全部证据包总字数**，单位为倍，越大越好。**只作为报告中的描述性指标，不作为验收门槛**——证据字数受 budget 硬约束，该值几乎完全由 budget 决定，量不出检索准不准。下界 = 总字数 ÷ (项数 × budget)，budget 3000 时为 15.3 倍。验收改用 §6 阶段一的三条效果指标。 |
| **未命中** | 某评分项在某家投标文件中检索不到任何合格证据。这是**正常且正确**的结果，表示该家未写此项内容，应判 0 分，而非系统故障。 |
| **未评定** | 与「未命中」完全不同：指调用大模型失败（重试耗尽后仍格式错、超时或拒答），系统**没能给出判断**。不得记 0 分，须在报告中单列。见 §4。 |
| **降级 / fallback** | 按细粒度检索词（二级要素）检索不到证据时，退到上一级（要素或评分项）的检索词重新检索。检索到的证据算弱证据。 |
| **S0~S4** | 系统的五个处理阶段，见 §3。 |

### 2.1 评分项与投标文件的绑定关系（本项目最重要的结构事实）

**评分项和投标文件是一一绑定的，不需要检索去猜、也不需要人工映射。**（依据：实测）

招标文件评标办法里每个评分项的描述，结尾都有一句「相关标书内容在《某某方案》中体现」；
投标系统据此把每家的技术标拆成固定的 20 个 PDF，文件名即评分项名，
文件名尾部带一个 GUID：

```
评分项（招标文件 p33~p37）      投标 PDF 文件名
设计任务书优化 20.0 分      ←→  设计任务书优化75BD5598-9F76-4E3B-8A0A-D494380D4D9D.pdf
进度管理方案   4.0 分       ←→  进度管理方案108D538F-85B8-4C7D-B32C-F6ACDAA187B9.pdf
```

- **12 家投标人的 20 个文件名完全一致**，是投标系统的固定模板，不是巧合。
- 20 个文件中 19 个对应评分项，第 20 个是封面（无分值）。
- **绑定有两条独立的路，任一条成立即可，不依赖外部提供的 xlsx：**
  1. **按名匹配**（主路）：招标文件的评分项名与 PDF 文件名前缀唯一对应，实测 19/19，
     未匹配的文件只有「封面」。文件名被系统截断到约 14 字，因此用前缀匹配而非全等。
  2. **按 GUID 匹配**（加固）：文件名尾部 GUID 与 `拆分评审项.xlsx` 的 `pb_item_guid` 相同。
     这条依赖拿得到那份 xlsx，正式测试时不作为前提（见 `docs/issues.md` 已决事项）。

**这条事实的后果：**「从一家 87 万字的标书里检索出某评分项的证据」这个问题，
降级成「打开对应的那一个 PDF（平均 5.5 万字）」。跨文件定位不再需要算法。
S2 的作用相应收窄为**在单个 PDF 内部按要素定位段落**，见 §3。

核对过程与证据见 `docs/findings-招标文件核对.md`，复现脚本 `scripts/verify_scoring_table.py`。

> **换项目时的降级路径**：以上绑定依赖投标系统按评分项拆分文件并以评分项名命名。
> 若换一个不这么拆的项目（例如整本技术标只有一个 PDF），按名匹配失效，
> 需退回「评分项 → 评审点 → 检索关键词」的人工映射路线，评审点库的编号规则见 §9.6。
> 该路线是否需要保留，见 `docs/issues.md` P2。

### 2.2 状态词判定标准

本文档及后续进度同步中，「已完成 / 进行中 / 未开始」按以下标准判定，不按主观感觉：

- **已完成**：代码已写、已在**代表性数据**上跑通、输出结果已人工检查过一遍。三者缺一不算。
- **进行中**：代码已开始写，但尚未跑通。
- **未开始**：无代码，或仅有本文档中的设计描述。

「代表性数据」指能触发该模块所有代码路径的真实文件，不要求与最终业务领域一致。
**代码跑通与效果达标是两件事**，效果指标单独在 §6 的完成判定里写明。

§8 阻塞项另用一套词（待确认 / 待申请 / 待澄清 / 待指派），含义在 §8 表内逐条给出解除条件，
与本节三档状态无关，不要混用。

## 3. 系统架构

五个阶段，串成一条流水线。每个阶段的中间产物落盘为 JSON/YAML 文件，可单独运行、单独检查、单独重跑。

```
                  ┌─> 评分表.yaml ──────┐
招标文件.pdf ─S0──┤                     │
（离线，见 §1.1） └─> 项目特征摘要.md ──┼──> S3 ──> 评审结果.json ──S4──> 报告
                                       │      ↑
投标文件*.pdf ──S1──> 章节树.json ──S2──> 证据包.json
（按 GUID 绑定到评分项，见 §2.1）      （每家投标人各跑一遍 S1/S2/S3）
```

虚线以上的 S0 在测试前离线跑完，只有 S1~S4 计入 §1 的 50 分钟。

| 阶段 | 做什么 | 为什么这么做 |
|---|---|---|
| **S0** 抽招标信息 | ① 从招标文件 PDF 抽出评分表（19 项、分值、三档区间），再按评分描述推导要素与权重；② 抽项目特征摘要。**人工确认后存盘。** | **离线执行，不计入 50 分钟**（§1.1）。因此不要求全自动、不要求当天跑通——人 + AI 协作产出一份 yaml、人工核一遍即可。评分表由我方自产，不依赖投标系统提供的 xlsx（2026-08-19 决策）。抽取目标明确：核对已证明 19 项、分值、三档区间全部是招标文件原文（19/19 一致，见 `docs/findings-招标文件核对.md`）。 |
| **S1** 投标文件入库 | 把每家的 20 个技术标 PDF 切成章节块 | 切分策略已定案（2026-08-19 实测）：**编号形式定层级 + 相对满行宽定标题**，见 §3.7。真实 PDF 无书签、单一字号、无加粗，编号是唯一可用的结构信号。**已实现**（T0，`src/s1_ingest.py`），见 §10.1 运行命令。 |
| **S2** 证据定位 | 在**评分项对应的那一个 PDF 内部**，按要素检索出证据单元，组成证据包，字数受 budget 约束 | 跨文件定位已由 GUID 绑定解决（§2.1），S2 只负责文件内压缩：把单个 PDF 平均 5.5 万字压到几千字。**这仍然是算力开关**——12 家 × 19 项 = 228 次调用，若整份 PDF 直接送模型，输入总量约 1047 万字。 |
| **S3** 逐项评审 | 每个证据包 + 项目特征摘要调一次大模型，输出判分、理由、引用编号 | 每项独立无状态，天然可并行。这是把总耗时压下去的最直接手段。 |
| **S4** 汇总出报告 | 多家并排对比表 + 逐项明细 + 性能数据 | 客户的实际交付物。注意是并排展示，不是系统做对比判断，见 §0。 |

**规模基数**：12 家 × 19 项 = **228 次 S3 调用**。此前文档中的「570 次」基于 3~5 家 × 114 项，已作废。

### 3.0 这是流水线，不是 agent

**本系统不使用任何 agent 框架，不做工具调用循环，不做记忆与自我反思。**

理由：S3 是 N 次**独立、无状态、固定流程**的调用（N = 投标人数 × 评分项数 = 12 × 19 = 228），
每次的输入在调用前已经完全确定（证据包 + 项目特征摘要 + 档位描述），
输出结构也已固定（§4 评审结果）。这里没有任何需要模型自己决定"下一步干什么"的环节。

上 agent 框架的代价是实打实的：多轮工具调用会让单项耗时翻倍以上，而 §1 的 P0 指标就是吞吐量；
同时引入不可控的 token 消耗和更多失败模式，而 §3.6 的重试逻辑要的恰恰是可预测的失败面。

因此 S0~S4 的实现形态是**五个可单独运行、中间产物落盘的脚本**，用普通的并发调度串起来。
（2026-08-18 决策，依据：录音。想引入 agent 框架之前，先说明哪个环节需要模型自主决策。）

**这不是原则问题，是本次约束下的取舍。** 任务里确实有三处存在真正的自主决策点：

1. **未命中时自主换词重检索**——现在走固定降级（二级要素 → 要素 → 评分项）。
   让模型判断「要找的是进度纠偏机制，没搜到，换个说法」，大概率优于固定降级。
2. **证据不足时主动索取更多**——现在 budget 卡死 3000 字，截断只打 `truncated` 标记。
   agent 版本可以要求追加相邻章节再判。
3. **判分后自检**——「我判了优档，但引用的证据里没有规范编号」这类反思。

不做它们的原因是**换不起耗时**：每项从 1 次调用变成 3~5 次，总数从 228 涨到 900 多，
§6 阶段二那个 `单次耗时 ÷ 并发路数 ≤ 13.2 秒` 的约束收紧到 3.3 秒，
30 秒/次就需要并发 9 路以上。**吞吐量是 P0，分数准确度是 P2，用 P0 换 P2 算不过来。**
另外循环轮数不固定意味着总耗时无法预估，而页面③要显示「预计剩余」，客户盯着看。

**什么条件下该改（具体条件，不是拍脑袋）：**

- T9 实测后若单次调用很快（如 5 秒）、预算有富余，可**只对未命中的项**加一轮自主重检索。
  未命中通常是少数，不影响总账。这是最值得先试的一处。
- 阶段三做分数校准时，自检循环有价值，那个阶段没有 50 分钟约束。

**对外材料里出现「智能体」「调用 Skill」这类措辞时，注意它指的是本流水线，不是 agent 循环。**
2026-08-19 的辅助评审流程图中，「辅助评审智能体」一个方框对应本文的 S1+S2+S3+S4 全部，
「调用 Skill」对应 S0 的离线拆分。命名口径的分歧已登记在 `docs/issues.md` P1——
对外这么说没问题，但照着那张图去搭 agent 框架就是架构分歧。

### 3.1 当前实现与目标架构的差异（重要，动手前必读）

上面的架构图描述的是**目标状态**。S1（PDF 入库）已由 T0 完成（`src/s1_ingest.py` 支持 PDF，
真实数据 240 个投标 PDF 已跑通）；S2 尚跑在**软件信息化类样例**上，不是真实的工程施工类文件。
剩余差异如下：

| S2 的检索范围 | 评分项对应的**单个 PDF** 内部（GUID 绑定，§2.1） | 一家的全部章节块（2121 块）混在一起检索 |
| S2 的输出 | 完整证据包，含 `bidder`、`item_id` | 缺 `bidder` 和 `item_id`（只有 `point_id`），因为尚不支持多家 |
| 跑一次的规模 | 12 家 × 19 项 = 228 次 | 1 家 × 114 项 |
| 项目特征摘要 | 注入每次 S3 调用 | 不存在，S0 未做 |

**所以：跑 §10 那三条命令，用的是 `原始资料/公司的临时样例文件仅作参考/` 下的软件类样例，
得到的 `located.json` 是 §4「证据包」结构的子集，不是最终形态。**
它验证的是检索算法本身能不能跑（§3.2 三条红线由 `tests/test_s2_regression.py` 守住），
不代表在真实工程标书上的效果——效果验证的前提是 S2 适配多投标人（§7 的 T8）。

### 3.2 三条设计红线

以下三条是 S2 在真实文件上验证出来的结论。**每条都有对应的回归测试**（`tests/test_s2_regression.py`），
改坏了测试会红。改动前请先跑一遍测试，再按「复现方式」把反例跑出来看一眼。

复现基于 §10 的前两条命令产出的数据，修改 `src/s2_locate.py` 的常量后重跑第三条命令。

**为什么不用 BM25，也不用向量检索。** 最初的方案是 BM25。实际没用，原因是两条红线 BM25 给不了：

- BM25 的核心增益是词频饱和与文档长度归一化。本项目的检索单位是章节块，中位数 301 字、
  分布集中，长度归一化基本不起作用；而红线一要解决的是**通用词没有区分度**，那是 IDF 那一半的事，
  BM25 的 tf 部分帮不上忙，反而让高频通用词更容易靠重复次数堆分。
- 红线二的**单锚点闸门是一票否决**，不是加权打分。BM25 是纯打分模型，没有"这个词必须出现，
  否则整段淘汰"这种语义，套上去还得在外面再加一层同样的闸门。

向量检索同理不用：本任务要的是「这段有没有写深基坑」这种字面事实判定，不是语义近似；
而且引入向量库会带来模型下载、显存占用和索引构建耗时，全都要从 §1 的 50 分钟预算里扣。

当前实现 = **IDF 加权求和（红线一）+ 单锚点一票否决（红线二）+ 父章节整段收取（§3.3）**。
想换回 BM25 或上向量库之前，先说明它怎么满足红线二。

**红线一：词权重必须用 DF 占比，不能用词频、覆盖率，也不能用 IDF 绝对值。**

> **DF 在哪个范围上统计：该家投标人的全部 20 个 PDF（约 3,635 个章节块）。**
> 检索范围和统计范围是两件事——**检索只在评分项对应的那一个 PDF 内进行（§2.1 的 GUID 绑定），
> 但词的 DF 在该家全部文件上算。**
>
> 理由是统计分辨率。单个 PDF 中位只有 111 个章节块（§3.7 实测），
> 一块就占 0.9%，`ANCHOR_DF_RATIO = 0.05` 落在 5.6 块上——
> **一个词出现 5 次还是 6 次就能翻转锚点资格**，DF 占比在这个样本量上照样漂，
> 只是漂的原因从「语料规模」换成了「样本太小」，红线一的立论会被架空。
>
> 取该家全部 20 个 PDF 约 3,635 块，与当前阈值标定时用的 2121 块同量级，
> **阈值语义不变，不需要重新标定**。
> 不取 12 家合池（43,623 块）的原因有二：加一家要全部重算、断点续跑失效；
> 且 12 家写的是同一个项目的应答，共性内容的 DF 会被推高，一批本该合格的锚点会掉出门槛。
>
> 这条约束落在 §7 的 T8，其完成判定里已写明。

原因有两层。

其一，长评审点名切词后得到「总体 / 设计 / 方案 / 施工」这类通用词，任何一段中文技术文档都能覆盖
80% 以上，覆盖率完全没有区分度。按 DF 压低通用词权重后，实测自动滤掉 35 个词
（含「方案」「措施」「安全」「施工」），省掉了手工维护停用词表这件事。

其二，阈值必须用 **DF 占比**而非 IDF 绝对值。IDF 绝对值随语料篇数变化，同一个词在 20 篇语料和
2000 篇语料里能差一倍，阈值就成了随语料漂移的魔数，换一批标书就得重调。
当前两个阈值：`MAX_DF_RATIO = 0.22`（超过 22% 的章节都有的词丢弃）、
`ANCHOR_DF_RATIO = 0.05`（低于 5% 才够格当锚点）。

反例（实测）：改用词覆盖率打分时，`①-1「施工组织总体设计」`匹配到了「月度总结会制度」，
`⑩-1「深基坑工程」`匹配到了「概要设计方案评审」。

复现方式：把 `score_section()` 中按 `idf.get(t, 0)` 加权的部分改成固定权重 1.0，
把 `MAX_DF_RATIO` 设为 1.0，重跑，看 `①-1` 和 `⑩-1` 命中了什么。

**红线二：锚点词只取最罕见的那一个；DF 为 0 时直接判未命中，不换词。**

第一半：取一批高区分度词再判断「命中任意一个」，等于其中最通用的那个词说了算，闸门形同虚设。
实测中 `⑩-1「深基坑工程」`靠「可行性」一词凑够分数，仍匹配到无关章节，候选数 24；
改成单锚点后候选数降到 1，且那 1 个章节是真的写了「深基坑」。

第二半更反直觉，是一次错误修复换来的：**DF=0 的词不能排除，它恰恰是最强的信号。**
DF=0 意味着这个概念在本份标书里根本不存在，应当直接导向未命中。
曾因为担心同义词问题（评审点写「四新技术」、标书写「新技术、新工艺」）而把 DF=0 的词
排除出锚点候选，结果 `①-2「施工现场平面布置」`的锚点从 DF=0 的「平面布置」退到了
DF=9 的「布置」（出现在「布置任务」之类的地方），放行了一整段完全无关的验收交付章节。

**同义词问题的正确解法是在评分表的 `synonyms` 字段里补同义词（§4），不是让检索靠换词去猜。**

复现方式：把 `anchor()` 的候选过滤改回 `1 <= df.get(t,0) <= n * ANCHOR_DF_RATIO`
（即排除 DF=0），重跑，观察 `①-2` 从未命中变成命中一段无关内容。

**红线三：必须允许未命中，且未命中由两道独立防线保证。**

投标文件确实没写这一项时，正确行为是返回零证据、该项判 0 分。
硬凑一段不相关原文喂给模型，正是「应得 5 分判成 8 分」这类错误的来源，而这是 §1 里的 P0 红线。

两道防线，缺一不可：

1. **锚点 DF=0** —— 该概念在文件中不存在（红线二第二半）
2. **`MIN_SCORE` 分数门槛** —— 词都出现过，但整体相关性不够

现状：当前实现下 `①-2 施工现场平面布置和临时设施、临时道路布置` 正确落空，
因为手头样例是软件标，确实没有这项内容。这是正确行为，不是 bug。

复现方式：把 `MIN_SCORE` 调到 0 并把 `ANCHOR_DF_RATIO` 调到 1.0，重跑，未命中数会变成 0——那才是 bug 状态。

### 3.3 证据按父章节整段收取

章节块中位数只有 300 字（实测值，来自 §10.2 的 docx 样例；PDF 切分后的分布尚不可知），
一个评分项的内容常横跨十几个相邻小节。逐块收会收到一堆互不相邻的碎片，
喂给模型的上下文是跳跃的。因此 S2 检索在细粒度块上做，**收取时按整个父章节收**。

**PDF 路径下本节同样成立，且实测反而加强了它。** §3.7 的切分方案由编号形式给出层级，
父子关系存在。更重要的是：在 228 个真实 PDF 上实测了「固定第 N 级标题」的聚合效果，
单元字数 P90 达 23,003 字、最大 278,553 字（budget 是 3000 字）——
因为有的文档根本没有 `第N章` 这一级。**固定层级在真实数据上彻底失效，直接父章节自适应。**
详见 `docs/findings-pdf切分探针.md` §五。

用「直接父章节」而不是固定的第 N 级标题：投标文件标题深度各不相同，固定层级会把深层小节
归并到大章之下，单元过大，排序被大单元里的偶然高分块带偏（实测发生过：
`③-1 安全生产管理体系`的最佳证据「安全管理组织」被归到了「6、验收交付节点」这个大章下。
该反例来自 §10.2 的 docx 样例）。父章节这个粒度随文档结构自适应，也省掉一个需要调的参数。

### 3.4 项目特征摘要：判「针对性」的前提

评分档位普遍长这样：「5 分：阶段划分清晰、**针对本项目**、有规范依据」。
录音里也明确「有没有针对这个项目提出具体的意见，这就是一维」。

**如果 S3 的输入只有档位描述和投标文件片段，模型手里没有「这是个什么工程」的任何信息**——
河道还是房建、什么地质、工期多长、重难点在哪——它只能判「写没写」，判不了「针对不针对」。
而针对性恰恰是 5 分和 3 分的分界线。

因此 S0 除了抽评分表，还要抽一份 300~500 字的**项目特征摘要**，作为全局上下文注入每一次 S3 调用。
500 字 × 228 次约增加 8 万 token，占总量比例很小，但这是「针对性」这一维能不能判的前提。

### 3.5 防幻觉：引用用选择，不用生成

**模型不输出原文，只输出证据编号。**

证据包里的每个章节块带一个序号，模型输出 `"cite": [2, 5]`，原文由系统按序号从章节块里截取。

不这么做的话——让模型自由输出 `quote` 再回原文做字符串匹配——中文模型极大概率会改写而非
逐字复制（顺手把「三个施工段」写成「三段施工」），于是大批引用校验失败，
`confidence` 全线打折，所有项都标「建议人工复核」，信号全糊掉等于没做。

**把生成改成选择，幻觉从根上不存在**，不需要事后检测，还省下吐原文的 token。
系统仍校验编号是否在证据包范围内，越界即判该次调用失败并重试（§3.6）。

### 3.6 调用失败：先重试，重试耗尽才记未评定

228 次调用里必然有失败的：JSON 格式错、超时、模型拒答、引用编号越界。

**处理顺序是重试优先，不是直接记未评定：**

1. **重试 3 次**，退避间隔 2 秒 / 4 秒 / 8 秒。格式错误的重试请求里附上上一次的错误信息。
2. 3 次仍失败 → 该项标记为**未评定**（`status: "unrated"`），`score` 置 null。
3. **未评定不等于 0 分。** 0 分表示投标人没写，未评定表示系统没判出来——把模型的问题算成投标人的问题是错的。
4. 未评定项在页面③实时显示、在页面④单独用符号标出、在报告中单列一节，不混进分数统计。

全流程跑完后允许对所有未评定项发起一轮统一重跑，这一轮同样计入总耗时。

### 3.7 PDF 怎么切块（已定案，2026-08-19 实测）

完整依据与实测数据见 `docs/findings-pdf切分探针.md`，复现脚本 `scripts/probe_pdf_structure.py`。

**先排除两条路**（实测 228 个 PDF、40.5 万行）：

- PDF 无书签，`get_toc()` 全部返回空。
- **全文单一字号 12.0pt，加粗行 0%**——投标系统生成 PDF 时抹平了所有字体格式。
  因此按字号或加粗推断标题完全不可行。

**剩下的唯一信号是行首编号**，层级直接由编号形式给出：

| 层级 | 编号形式 | 例 |
|---|---|---|
| 1 | `第N章` / `第N节` | 第二章、施工组织总体设想和部署 |
| 2 | 中文数字 + `、` | 一、工程概况 |
| 3 | `N、` / `N.` | 1、编制说明 |
| 4 | `N.N` / `N.N.N` | 2.6.1、国家规范、标准 |
| 5 | `（N）` / `（一）` | （1）给水系统工艺流程 |

**但编号本身不够**，正文里大量段落也以编号开头：

```
标题： 1.1工程概况简述
正文： 1.1、采用分段流水施工作业，确保重点分项工程和关键工序的施工进度，根据本工
```

区分靠**行长**：PyMuPDF 的「行」是视觉换行，正文段落被硬折到满行宽，首行几乎总是顶满；
标题提前结束所以短。

**标题判定规则：匹配上表任一编号形式，且行长 < 0.8 × 本文档行长的 P90（满行宽）。**

阈值相对于每份文档自己的行宽，不是绝对字数——各文档满行宽实测 37~38 字不等，
写死会随排版漂移。这与 §3.2 红线一用 DF 占比而非 IDF 绝对值是同一条原则。

**切出来的粒度**：每份 PDF 中位 111 个章节块，块字数中位 114 字
（docx 路径为 301 字，同量级）。因此 `src/s2_locate.py` 不需要改。

**碎块不用单独处理**：表格类内容会被切得很碎（最极端的一份块字数中位数只有 4 字），
但 §3.3 的父章节整段收取会把它们吸收成段。表格的行列语义丢失是已知代价，
影响面与是否值得专门处理见 `docs/issues.md` P1。

**选定方案聚合后的实测分布**（228 个 PDF、9,214 个证据单元，budget = 3000 字）：

| 指标 | 直接父章节聚合（选定） | 固定层级 1~2 聚合（已否） |
|---|---|---|
| 单元字数中位数 | **433** | 1,723 |
| P75 | 1,219 | — |
| P90 | **2,659** | **23,003** |
| 最大 | 77,053 | 278,553 |
| 超过 budget 3000 字的比例 | **8.2%** | — |

**P90 落在 budget 之下，§3.3「整段收取」的设计意图成立**——九成的证据单元能完整装进证据包，
不被截断。超出的 8.2% 走 §4 的 `truncated` 标记与 `confidence` 打折。
这是 T0 的验收依据之一。

## 4. 数据契约

以下五个结构是模块之间的全部接口。改这些结构等于改接口，需同步改上下游；改其他任何东西都不影响别的模块。

标注「设计」的字段表示该模块尚未实现，此处为约定；未标注的表示当前代码已产出。

**章节块**（S1 产出。当前实现基于 Word 标题层级；PDF 版切分策略未定，见 `docs/issues.md` P0）

```json
{"id": "3#47",
 "file": "施工方案及技术措施123A9226-D66E-4ACE-8DC4-65A76A8282FA.pdf",
 "item_guid": "123a9226-d66e-4ace-8dc4-65a76a8282fa",
 "path": ["第二章 施工组织", "2.1 总体部署", "2.1.4 施工段划分"],
 "level": 3,
 "page": 12,
 "text": "本工程划分为三个施工段……",
 "char_len": 1840}
```

- `id` 格式为 `文件序号#块顺序号`，**只在单个投标人范围内唯一，不是全局唯一**。
  **`#` 后面是该块在本文件内的出现顺序（第几个），不是文档里的章节编号。**
  例：`3#47` = 第 3 个文件的第 47 个章节块，它的章节编号可能是「2.1.4」，写在 `path` 里。
  实测值形如 `6#11`。
- **跨投标人引用一律用 `(bidder, id)` 复合键，这是全系统所有引用的锚。**
  原因是 12 家共用同一套 20 个文件名、连文件名尾部的 GUID 都相同（§2.1 的投标系统固定模板），
  而 `文件序号` 是 S1 本次运行时的位置序号——按家分别跑 S1，每家都从 `1#1` 重新开始。
  因此 `file`、`item_guid`、`id` 三者单独都区分不了投标人，必须带 `bidder`。
  合并时**不重写 `id`**，见下方「章节块全量索引」。
  （2026-08-19 决策。另一条路是合并时把 `bidder` 拼进 `id` 使其全局唯一，
  已否决：那样 `id` 会随合并顺序变化，断点续跑重跑一家就会让该家全部引用失效。）
- `item_guid`：**设计**。取自文件名尾部的 GUID（小写），把该块直接绑定到评分项，见 §2.1。
  当前实现没有此字段，因为样例文件是 docx、不带 GUID。
- `path` / `level`：docx 路径来自 Word 标题层级；PDF 路径由行首编号形式给出，取值 1~5，见 §3.7。
- `page`：**该块起始行所在的 PDF 页码，从 1 开始。** 页面⑤的「在原文中定位」靠它跳转（§5.3）。
  **T0 实现时必须一并输出**——切完再补要重跑 241 个 PDF。docx 路径无此字段，填 null。

**章节块全量索引**（S1 合并产出，`data/projects/<slug>/sections_all.json`）

S1 按投标人分别产出 `sections.json`，再用 `scripts/merge_sections.py` 合并成全量索引。
顶层为对象，内部 `sections` 数组的每个元素在单家章节块基础上注入 `bidder` 字段：

```json
{"project": "济阳区实验高级中学项目工程总承包（EPC）",
 "project_slug": "jiyang-epc",
 "schema_version": "1.0",
 "generated_at": "2026-08-19T17:28:00+0800",
 "bidders": ["sample-docx"],
 "sections": [{"bidder": "sample-docx", "id": "1#4", "file": "1",
               "path": [...], "level": 4, "text": "...", "char_len": 652}],
 "stats": {"total_sections": 2121, "total_chars": 1405322,
           "by_bidder": {"sample-docx": {"sections": 2121, "chars": 1405322}}}}
```

- `bidder`：取值与 `manifest.json` 里的 `bidders[].id` 一致，真实场景为投标文件所在一级目录名。
- `id` 在单家范围内唯一；跨投标人引用时以 `(bidder, id)` 为复合键，合并时不重写。
- 这是 S1 -> S4 的汇总节点，S2 仍按单个 bidder 的 `sections.json` 独立跑。

**评分表**（S0 产出，一个项目一份，人工确认过。设计）

顶层是一个映射，不是裸列表：项目级规则（招标文件里那些「适用于所有评分项」的话）
需要有地方安放，否则页面②录进去的整体规则无处可存。

下面的示例取自本次实测项目的真实数据（依据：实测）：

```yaml
project: 济阳区实验高级中学项目工程总承包（EPC）
source: 招标文件.pdf 第 33~37 页       # 这张评分表抽自哪里，人工确认时核对用
rules:                                 # 项目级规则，注入每次 S3 调用，对全部评分项生效
  - 内容不全酌情扣分
  - 若此条缺项不得分
items:
  - id: T-02                           # 评分项编号，本项目内唯一
    guid: 108d538f-85b8-4c7d-b32c-f6acdaa187b9   # 与投标 PDF 文件名尾部 GUID 相同，见 §2.1
    name: 进度管理方案
    max_score: 4.0
    tiers:                             # 三档，按分值降序。每档是**区间**，不是单一分值
      - {tier: 优,   min: 3.0, max: 4.0, desc: ...}   # 最高档：闭区间 [3.0, 4.0]
      - {tier: 良,   min: 2.0, max: 3.0, desc: ...}   # 左闭右开 [2.0, 3.0)
      - {tier: 一般, min: 1.0, max: 2.0, desc: ...}   # 左闭右开 [1.0, 2.0)
    factors:                           # 要素，权重和 = 1.0。见 §2 术语表「要素 / 二级要素」
      - name: 施工进度计划编制与关键路径分析
        weight: 0.35
        sub:                           # 二级要素，权重和 = 1.0，同时是 S2 的检索粒度
          - {name: 总体进度计划合理性, weight: 0.4, desc: ...}
          - {name: 关键路径与里程碑节点控制, weight: 0.35, desc: ...}
          - {name: 工序衔接与流水施工组织, weight: 0.25, desc: ...}
    synonyms: [香蕉曲线, S曲线]         # 同义词扩展，补标书实际会用的说法。见 §3.2 红线二
```

字段说明：

- **`tiers` 是区间不是单值。** 招标文件对全部 19 项统一写「分为一般、良、优，
  分别酌情得 X-Y 分、Y-Z 分、Z-W 分」。因此 `score` 是区间内的连续值，
  §1 的 P0 红线「档位不能错」指的是**落错区间**，区间内的差异不作为错误。
- **区间边界归属：除最高档外一律左闭右开 `[min, max)`，最高档为闭区间 `[min, max]`。**
  招标文件原文写的是「1-2 分、2-3 分、3-4 分」，字面上首尾相接，2.0 同时属于两档。
  数据契约必须消歧，否则判出 3.0 分时 `tier` 填什么无定义，
  §6 阶段三的「档位一致率」也算不出来。**这是我方的实现约定，不改变招标文件的分值范围。**
- `guid`：主键，把评分项与投标 PDF 绑定，见 §2.1。缺它则退回人工映射路线。
- `factors`：要素与二级要素及权重。**招标文件里没有这一层**，由我方从评分描述推导
  （2026-08-19 决策：自建，福莱通那份仅作对照参考）。它有两个用途——S2 的检索粒度，
  以及区间内定分的加权依据。
  **拆分不求精确**：客户已明确「先测一测就行，起码有个结果就行」，
  做法是大模型按统一 prompt 从评分描述拆、权重等权或粗给。离线产出，见 §1.1。
- `rules` 与 §3.4 的项目特征摘要都是全局上下文，但两者不可互相替代：摘要描述**这是个什么工程**
  （用于判「针对性」），`rules` 描述**判分时必须遵守的硬约束**（用于避免该扣的分没扣）。
  本项目的两条 `rules` 是招标文件原文，其中「若此条缺项不得分」使
  §3.2 红线三的「未命中判 0 分」从设计选择变成招标方的明文要求。

**项目特征摘要**（S0 产出，一个项目一份。设计）

纯文本，300~500 字，注入每次 S3 调用。内容要求：工程类型与专业、建设规模、
场地与地质水文条件、工期要求、招标文件明确点名的重点难点。

**证据包**（S2 产出）

```json
{"item_id": "T-02", "item_guid": "108d538f-85b8-4c7d-b32c-f6acdaa187b9",
 "bidder": "中冶建工集团有限公司8010856",
 "name": "进度管理方案",
 "candidates": 32, "units": 3, "fallback": false,
 "evidence_chars": 2860, "budget": 3000,
 "picked": [{"section_id": "3#47",
             "file": "进度管理方案108D538F-85B8-4C7D-B32C-F6ACDAA187B9.pdf",
             "path": ["第二章 施工组织", "2.1 总体部署", "2.1.4 施工段划分"],
             "unit": ["第二章 施工组织", "2.1 总体部署"],
             "page": 12,
             "match_score": 21.7, "hit": ["t:关键路径", "b:施工段"],
             "chars": 1840, "truncated": false}
            ]}
```

> 示例中 `picked` 只列出 1 条，实际应有 `units: 3` 个证据单元、合计 `evidence_chars: 2860` 字，
> 其余条目已省略。字数与条目数在真实输出里必须自洽。

字段说明：

- `item_id` / `item_guid` / `bidder`：**设计**。当前实现无这三个字段，原因见 §3.1。
  **`bidder` 的取值 = 投标文件所在的一级目录名，原样照抄，含尾部的投标编号**
  （例 `中冶建工集团有限公司8010856`，定义见 §2 术语表）。
  它是 §4 报告数据里 `matrix` 与 `totals` 的键，**12 家写法必须完全一致**——
  截断、去空格或改写会把并排表拆成多列。T8 补齐该字段时按此取值。
  当前实现输出的是 `point_id`（评审点 id），本项目用不到评审点，见 §2.1。
- 检索范围：**该评分项 `item_guid` 对应的那一个 PDF 内部**，不跨文件（§2.1）。
- `candidates`：通过门槛的候选章节块总数。`units`：收取的证据单元数。
- `fallback: true`：走了降级检索（二级要素检索不到，退到要素或评分项级），属弱证据，S3 需据此降低 `confidence`。
- `evidence_chars` / `budget`：本包实际字数 / 上限字数。顶到 budget 说明证据被截断，可能漏内容；
  远小于 budget 说明这项在投标文件里着墨很少。
- `picked`：按文档原顺序排列，**同一 `unit` 的块相邻**。`picked` 的数组下标即 §3.5 的引用编号。
- `section_id`：该块在章节块里的 `id`。**它只在单家范围内唯一**，回查原文时必须配本证据包顶层的
  `bidder` 一起用，即复合键 `(bidder, section_id)`，理由见本节「章节块」的 `id` 字段。
  页面⑤的「在原文中定位」按这个复合键跳转（§5.3）。
- `unit`：该块所属证据单元的路径，即其直接父章节。
- `page`：透传自章节块，供页面⑤跳转 PDF 页用。
- `match_score`：检索匹配分，IDF 加权和，无上界，**仅用于排序和过滤，不参与判分**，
  与评审结果里的 `score`（判分）是两回事。低于 `MIN_SCORE`（当前 8.0）的块不进候选。
- `hit`：命中详情。前缀含义——**大写 = 完整短语命中，小写 = 单词命中；T/t = 命中标题链，B/b = 命中正文**。
  「短语」与「单词」的界线是可判定的：**短语 = 检索词条目本身**（评分表里的一条要素名、
  二级要素名或 `synonyms` 条目），整条原样出现在文本里才算；
  **单词 = 该条目切分后的成分词**，单个成分出现即算。
  例：条目「施工进度计划编制与关键路径分析」整条出现记 `T:施工进度计划编制与关键路径分析`；
  只出现切出来的「关键路径」则记 `t:关键路径`。
  代码位置：`src/s2_locate.py` 的 `score_section()`，`phrases` 参数是短语、`terms` 是成分词。
- `truncated: true`：该块因 budget 用尽被截断，只取了前 `chars` 个字。

**评审结果**（S3 产出，交付物的原子。设计）

```json
{"item_id": "T-02", "bidder": "中冶建工集团有限公司8010856",
 "status": "rated", "tier": "良", "score": 2.6,
 "factor_scores": [{"name": "施工进度计划编制与关键路径分析", "weight": 0.35, "value": 0.7},
                   {"name": "设计进度管理与协同机制", "weight": 0.25, "value": 0.5}],
 "cite": [0, 2],
 "reason": "有总体进度计划与关键路径，但设计与施工的进度协同机制未结合本项目 EPC 模式说明",
 "confidence": 0.7,
 "attempts": 1,
 "perf": {"in_tokens": 3400, "out_tokens": 180, "latency_ms": 8200}}
```

字段说明：

- `status`：`rated`（已评定）/ `unrated`（未评定，见 §3.6）。
  `unrated` 时 `score` 必须为 null，**不得填 0**。
- `tier`：档位，取值必须是该评分项 `tiers` 里的 `tier` 之一（一般 / 良 / 优）。
  **判错档位是 §1 的 P0 红线**，档位内的分值差异不作为错误。
- `score`：判分，必须落在 `tier` 对应区间内（边界归属见本节评分表 `tiers`）；
  或为 0（未命中，即证据包为空）。

**档位与分数各由什么决定（这是判分机制的核心，实现前必须读）：**

| 环节 | 由谁决定 | 依据 |
|---|---|---|
| `tier` 落哪一档 | **模型判定** | 招标文件的档位描述原文 + 证据包 + 项目特征摘要 |
| `score` 在档内的位置 | **要素加权算出** | `score = tier.min + 得分率 × (tier.max - tier.min)` |

**为什么档位归模型判、不由得分率的阈值决定**：让得分率定档位需要一组阈值
（「0.61 属良、0.8 属优」），而定这组阈值要有专家评分作基准——我方一份都没有，
本次也不采集（§1 的 P2 已定不追求分数与专家一致）。
**拍一组没有依据的阈值去决定 P0 红线，比让模型对着招标文件的档位原文判更危险。**
档位描述是招标文件原文，模型直接对照判，这条链最短、可追溯。

**两个信号打架时怎么办**：模型判了「优」而要素得分率只有 0.15，
或判了「一般」而得分率 0.9——这说明档位判定与要素评价互相矛盾。处理方式：

- **不推翻模型的档位判定，不重试。** 重试只针对格式错与越界引用（§3.6）。
- 该项 `confidence` 再 ×0.7，从而必然低于 0.85 阈值，在页面④标 ⚠ 建议人工复核。
- 触发条件写死：**判最高档而得分率 < 0.3，或判最低档而得分率 > 0.7。**

`score` 的计算示例：判「良」（区间 [2.0, 3.0)）、得分率 0.61 →
`2.0 + 0.61 × 1.0 = 2.61`，保留一位小数记 2.6。
- `factor_scores`：**设计**。各要素的得分率（0~1），与评分表 `factors` 的 `weight` 加权后
  映射到 `tier` 区间内。这一层的必要性取决于 `docs/issues.md` 中要素权重那条 P0 的结论——
  若决定不使用要素分解，本字段删除，`score` 由模型直接在区间内给定。
- `cite`：引用的证据编号数组，取值为证据包 `picked` 的数组下标。原文由系统按此截取，模型不产出原文。
  编号越界视为本次调用失败，走 §3.6 的重试。
- `confidence`：置信度，取值 0~1，越大越可信。起始 1.0，按以下**四个**减分因素相乘：

  | 代号 | 触发条件 | 乘数 |
  |---|---|---|
  | 降级 | 证据包 `fallback: true` | ×0.7 |
  | 截断 | 存在 `truncated: true` 的证据 | ×0.9 |
  | 重试 | `attempts > 1`（重试过才成功） | ×0.9 |
  | 打架 | 档位判定与要素得分率矛盾（判最高档而得分率 < 0.3，或判最低档而得分率 > 0.7） | ×0.7 |

- **`confidence < 0.85` 的项在报告和界面上标记为「建议人工复核」**（页面④的 ⚠ 标记）。

  **阈值取 0.85 是算出来的，不是拍的。** 四个因素的全部非空组合共 15 种，按取值归并如下：

  | confidence | 对应组合 | 是否标 ⚠ |
  |---|---|---|
  | 0.900 | 仅截断；仅重试 | **否** |
  | 0.810 | 截断+重试 | 是 |
  | 0.700 | 仅降级；仅打架 | 是 |
  | 0.630 | 降级+截断；降级+重试；打架+截断；打架+重试 | 是 |
  | 0.567 | 降级+截断+重试；打架+截断+重试 | 是 |
  | 0.490 | 降级+打架 | 是 |
  | 0.441 | 降级+打架+截断；降级+打架+重试 | 是 |
  | 0.397 | 四者全中 | 是 |

  即阈值 0.85 等价于两条等价的可读规则，取其一即可：

  - **除「仅被截断」与「仅重试过」两种情形外，一律标 ⚠**；或
  - **走了降级检索、或档位与得分率打架、或任意两个减分因素叠加，就标 ⚠。**

  **改乘数或加新因素时，必须重算这张表并同步阈值。** 否则会出现阈值永远触发不到的情况——
  最初的 0.6 就是如此（当时三因素下唯一低于它的组合是 0.567）。
  这条规矩本身被违反过一次：加入第四个因素「打架」时未同步本表，
  由一次冷读检查发现，故在此留档。
- `attempts`：实际调用次数，1 表示一次成功。
- `perf`：该次调用的性能数据，逐项累加即为 §1 的吞吐量指标。

## 5. 界面与交互逻辑

### 5.1 界面设计的唯一硬约束

**客户会站在旁边盯着屏幕看，判断这是不是真在跑。**（依据：录音）

因此：进度必须实时、逐项滚动、显示当前正在评哪一项和已用时间。
**一个转圈的 loading 动画等于没做。** 这是产品硬需求，不是技术细节。

「实时」的判定标准：**每完成一个评分项，1 秒内必须出现在滚动区**；
滚动区连续 30 秒无新条目时，需显示当前正在处理的项目名与已等待时长，而不是让界面看起来卡死。

### 5.2 技术栈

**尚未确定，见 §8 的 B6。** 在确定之前，§5.3 的五个页面先做成不依赖后端的静态 HTML 原型
（假数据、可点击、可演示交互），用于确认交互逻辑并给出前端实现参照。
原型只需现代浏览器可打开，不引入构建工具。

### 5.3 页面流

```
① 新建评审  →  ② 确认招标信息  →  ③ 运行监视  →  ④ 结果并排  ⇄  ⑤ 单项详情
                   （人工介入）
```

以下线框中的所有数字（字数、耗时、显卡型号、分数）均为**占位示例**，不代表实测值或已确定的配置。
显卡型号尤其如此——算力规格实际尚未确定，见 §8 的 B3。

## 6. Roadmap

阶段之间是依赖关系，不是时间切分。每个阶段写明「做完的判定标准」，没有判定标准的阶段不算阶段。

### 阶段一：链路跑通（目标 2026-08-19 至 2026-08-20）

**做完的判定标准：用本次实测项目的招标文件 + 1 家投标文件（20 个 PDF），
端到端跑出一份带证据引用的评审结果 JSON，且满足下面三条 S2 效果指标。**

| 指标 | 门槛 | 为什么是这条 |
|---|---|---|
| 证据包非空率 | ≥ 90%（19 项中至少 18 项检索到证据） | 招标文件为每项都设了分值，专业投标人极少整项不写。大面积未命中说明检索配置错了，见 §3.2 红线三 |
| 证据总字数 | ≤ 19 × budget（budget 3000 时即 ≤ 5.7 万字/家） | 这是送进模型的实际输入量，直接决定 §1 的吞吐量 |
| 人工抽查相关性 | 随机抽 10 项，证据与评分项主题相关 | 前两条都是量，这条是唯一验质的 |

**原判定「压缩比 ≥ 20 倍」已作废。** 原因不是数字定错，是这个指标在 GUID 绑定之后失去了意义：
压缩比 = 总原文字数 ÷ (项数 × 实际证据字数)，而证据字数受 budget 硬约束，
所以压缩比几乎完全由 budget 决定，**量不出检索选得准不准**。
它是从「跨一家 140 万字全文检索」那个旧设计继承来的——那时压缩比确实反映检索的选择性。
现在检索范围已由 GUID 缩到单个 PDF（§2.1），选择性由上表第三条来验。
压缩比保留为报告中的**描述性指标**，算法见 §2 术语表，不作为验收门槛。

### 阶段二：性能达标（目标 2026-08-21）

**做完的判定标准：12 家标书全量跑完（228 次调用），总耗时 ≤ 50 分钟（越小越好），
全程无中断，中途杀进程后能从断点续跑，且未评定项为 0。**

「全程无中断」按端点形态取不同的可判定表述——**因为 B3 若为远程托管，我方采集不到显存，
「不因显存溢出中断」这条既无法判定也无从预防**：

| 端点形态 | 判定表述 |
|---|---|
| 本地/可观测算力 | 不因显存溢出中断，且峰值显存记入报告 |
| 远程托管端点 | 不因端点限流、超时或连接中断而失败；触发限流时按 §3.6 重试并记入 `retries` |

端点形态取决于 B2，见 §8。

「≤ 50 分钟」按全部投标人计（2026-08-19 决策），本次即 12 家。
**该预算只装 S1~S4，不含 S0 的离线准备**，界线见 §1.1。

**这个预算比按 114 项测算时宽松得多。** 约束是 `单次耗时 ÷ 并发路数 ≤ 13.2 秒`：

| 单次耗时 | 并发 2 路 | 并发 4 路 | 并发 8 路 |
|---|---|---|---|
| 15 秒 | 28.5 分 ✓ | 14.3 分 ✓ | 7.1 分 ✓ |
| 30 秒 | 57 分 ✗ | 28.5 分 ✓ | 14.3 分 ✓ |
| 60 秒 | 114 分 ✗ | 57 分 ✗ | 28.5 分 ✓ |

**风险点因此从「调用次数太多」转移到「并发路数够不够」**，而并发路数受显存限制。
T9 单点实测的重点相应改变：不只测单次耗时，要测并发 N 路时显存是否扛得住。

| 任务 | 完成判定 |
|---|---|
| 模型单点性能实测（T9） | 拿到单次调用的真实耗时与显存占用，据此重算并发路数与 budget |
| 两层并发（投标人 × 评分项） | 并发路数可配置，实测吞吐量随路数提升 |
| 重试与未评定处理 | 按 §3.6 实现；人为注入格式错误时能触发重试并最终标记未评定 |
| budget 调优 | 在 50 分钟预算内取到最大的 budget 值（字数越大精度越高） |
| 性能埋点 | 每次调用的输入/输出 token、耗时落盘；显存与卡型号若可采集则写入报告，不可采集则记「未采集」并注明原因 |
| 断点续跑 | 杀进程后重启能从断点继续，不重跑已完成项 |

**当前测算全部是推算，未经实测，风险已知：**
按每次 8 秒、并发 8 路计，228 次调用约 3.8 分钟。但 **8 秒这个数没有任何依据**。
3000 字输入在 20B 级模型上更可能是 15~30 秒。按上表，30 秒/次需要并发 ≥ 3 路才达标，
60 秒/次需要 ≥ 5 路。**并发路数能不能上去取决于显存**，这是 T9 要测的核心。
所以 T9 必须是 B2 解除后的第一件事，不能等全链路跑通才发现并发上不去——
那时候只剩砍 budget 一条路。

**另一笔账：不压缩会怎样。** 12 家技术标合计 1047 万字。若把每个评分项对应的整份 PDF
直接送模型，输入总量约 1047 万字（≈700 万 token）。压到 budget 3000 字后，
228 次 × 3000 字 ≈ 68 万字，是压缩比 15.3 倍——**这是 budget 3000 时的下界**，
因为 budget 是上限不是目标，着墨少的评分项装不满，实际压缩比会更高。
**注意这个数由 budget 直接决定，不反映检索质量**，所以阶段一的验收用的是上面那三条，不是它。

「档位一致」指系统判分与专家判分落在同一个 `tier` 内，不要求分值相同。**

## 9. 已知的原始资料缺陷

以下问题存在于甲方提供的原始资料中。**§9.1~§9.3 只影响评审点库，本项目已不使用评审点库**
（见 §2.1），因此这三条现在只对「换项目时的降级路径」有意义；§9.4 与 §9.5 仍然有效。

**9.1** `评审点.md` 中「②质量管理体系与措施」出现了两次，第一次 7 项、第二次 31 项，
且前者是后者的子集。当前按 114 个评审点处理（两份都保留）。确认后总数可能变为 107 或 138。
`tests/test_s2_regression.py` 里有一条断言锁定了 114 这个数，澄清后需同步修改。
澄清这件事本身登记为 §8 的 B7，已降级为非阻塞。

**9.2** 「④起重机械安全管理规范…」被排版成了大类，但从内容看它明显是
「③安全管理体系与措施」下的一个子项。这导致其后所有大类的编号顺延错位，
也就是说 §9.6 里的圈码与内容的对应关系目前是不可靠的。同样归入 §8 的 B7。

**9.3** `评审点.md` 里每个评审点的说明文字是同一段模板换名词生成的，
114 条全都是「基于招标文件及国家规范对 {X} 要求，总结…评审因素及评审点规则库…输出问题内容和判断理由」。
因此这份文档的实际信息量等于 114 个评审点名称。
**不要照着它写 114 个 prompt**，那会得到 114 个几乎一样的东西。真正的评分规则来自招标文件。

**9.4** 早期样例投标文件（`原始资料/公司的临时样例文件仅作参考/`）是软件信息化类标书，
不是工程施工类。实测该文件中「分部分项」出现 0 次、「工程量」8 次，而「系统」5251 次。
在它上面测出的压缩比为 4 倍（140 万字压到 33 万字），因为检索词与文件内容领域不匹配，
命中的多是勉强凑上的章节。**该样例仅可用于验证代码能否跑通，不可用于验证效果。**
（压缩比本身也已不作为验收门槛，原因见 §2 术语表与 §6 阶段一。）

**9.5** 从 PDF 抽表格必须处理跨页续行。核对招标文件评标办法时，
「各专业施工图设计的安排、协调、时间保证措施」一项的档位文本跨第 35/36 页分页
（`1.5-2` 断在页尾，「分」字落在下一页页首），按页取文本窗口会读进下一项的区间，
表现为**静默的假不一致**（比对结果显示 18/19，实际为 19/19）。
S0 从招标文件 PDF 抽取任何结构化内容时都需内建处理，见 `docs/issues.md` P2。

### 9.6 评审点库的编号规则（仅降级路径需要）

**本项目用不到本节。** 仅当换到一个不提供结构化评分表的项目、需要退回
「评分项 → 评审点 → 检索关键词」的人工映射路线时，才需要这套编号。

评审点只有**两级**，没有第三级：

```
①施工组织设计                        ← 大类，用圈码 ①②③… 标识
  1）施工组织总体设计，方案针对性…    ← 子项，在本大类内从 1 开始编号
  2）施工现场平面布置和临时设施…
②质量管理体系与措施
  1）质量方针与目标体系
```

- **评审点 id = `大类圈码-子项序号`。** 例：`①-1` 指第①大类下的第 1 个子项。
- 全部 114 个 id 及其检索关键词见 `config/review_points.yaml`，由 `评审点.md` 自动生成。
- 圈码共 **11 种（①~⑪）、出现 12 次**——② 出现了两次，这是原始资料的缺陷，见 §9.1 与 §9.2。

### 10.1 真实数据上现在能跑什么

**S1 入库（PDF 切块）能跑，S2 之后的链路仍跑不通**（S2 尚未适配多投标人，见 §7 的 T8）。

S1 把 12 家投标人的 240 个 PDF 切成章节块：

```bash
python src/s1_ingest.py "原始资料/实际测试工程文件/济阳区实验高级中学项目工程总承包（EPC） 2" data/projects/jiyang-epc/sections_all.json
```

预期输出 `合计 32,129 章节 / 9,819,249 字`，块字数中位数 179，39.4 秒，无报错。
验收核对脚本（需传入生成的 sections.json 路径）：

```bash
python scripts/verify_t0.py data/projects/jiyang-epc/sections_all.json
```

核对招标文件与评分表（19 行比对表）：

```bash
python scripts/verify_scoring_table.py
```

预期输出 `档位一致 18/19`。那一条不一致是跨页抽取误差，不是真差异，
原因与人工复核结论见 §9.5 与 `docs/findings-招标文件核对.md`。

探查 PDF 的结构信号（§3.7 切分策略的依据）：

```bash
python scripts/probe_pdf_structure.py
```

输出三份抽样 PDF 的字号分布、加粗比例与编号模式统计。
预期：字号 100% 为 12.0pt、加粗 0%，编号行占 15~28%。

### 10.2 样例数据上的三条命令（验证代码能跑，不验证效果）

用的是 `原始资料/公司的临时样例文件仅作参考/` 下的软件信息化类标书。
**这批数据只能证明代码不崩，不能证明检索效果**，原因见 §9.4。

```bash
python src/s1_ingest.py "原始资料/公司的临时样例文件仅作参考/ss投标/技术部分" \
  data/projects/jiyang-epc/sections/sample-docx/sections.json
```

目录下的 `.docx` 与 `.doc` 都会处理。`.doc` 会先自动转成 `.docx` 缓存到该目录的
`_converted/` 子目录（Windows 走本机 Word/WPS，其他平台走 LibreOffice 的 `soffice`），
两者都没有时直接报错退出并提示怎么办——不静默跳过文件。

```bash
python scripts/merge_sections.py data/projects/jiyang-epc
```

合并所有 bidder 的 `sections.json` 为 `sections_all.json`，作为全量章节索引；
S2 仍按单个 bidder 独立跑。

```bash
python src/build_points.py 评审点.md config/review_points.yaml
```

```bash
python src/s2_locate.py \
  data/projects/jiyang-epc/sections/sample-docx/sections.json \
  config/review_points.yaml \
  data/projects/jiyang-epc/evidence/sample-docx/located.json
```

预期输出：2121 个章节块 / 1,403,178 字；未命中 1 项（`①-2`，正确行为，见 §3.2 红线三）。
第三条命令的输出是 §4「证据包」结构的**子集**，差异见 §3.1。

## 11. 下一步做什么

如果你是刚接手这个项目的人或 AI，按这个顺序：

1. 读 §1，弄清这次考的是什么（不是分数准，是能真跑完）。
2. 读 §2.1，弄清评分项和投标文件是 GUID 绑定的——**这是本项目最重要的结构事实**，
   它决定了检索该怎么做，也解释了为什么评审点库用不上。
3. 读 §3.1，弄清当前实现和目标状态哪里不一样，**否则跑完 §10.2 的命令会对着输出发懵**。
4. 读 §3.2 的三条红线。要改 S2 的话，先跑 `pytest`，再按每条红线下面的「复现方式」把反例跑出来看一眼。
   红线二第二半（DF=0 不换词）尤其反直觉，那是一次错误修复换来的教训。
5. **T0（S1 支持 PDF）已完成**，真实数据已跑通（§10.1）。当前挡住真实数据跑通的是 **T8（S2 适配多投标人）**，
   前置是 T1 产出的评分表与 T7 的检索词，看 `docs/issues.md` 确认还剩哪些未决。
6. B2 一解除，**立刻做 T9 单点性能实测**——整个 §6 阶段二的算力账都建立在一个没有依据的 8 秒/次上。
7. T1（**从招标文件抽评分表**，离线产出，见 §1.1）前置已具备，可立即开工；T5/T6 静态原型同理。
8. T8 完成后，用真实素材跑 S1→S2，验证 §6 阶段一判定标准里的三条 S2 效果指标。
9. 然后按 §7 走两条关键路径：数据线 T8 → 效果验证，模型线 B2 → T9 → T2。分工见 `docs/分工与排期.md`。
