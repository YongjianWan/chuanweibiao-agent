## 0. 一句话

**输入** 一份招标文件 + 多份投标文件（同一个工程建设项目的多家投标人），
**输出** 每家在每个评分项上的得分、判分理由、以及理由所依据的投标文件原文出处，
外加一份性能数据（耗时、token 量，显存若可采集则一并给出）。

本次实测项目为**济阳区实验高级中学工程总承包（EPC）**，**12 家投标人**，
技术标 19 个评分项、满分 100 分。（依据：实测，见 `docs/findings-招标文件核对.md`）

**这不是串标围标识别系统。** 项目目录名叫「串围标智能体」，但本次交付的实际内容是
上面描述的技术标辅助评审打分。串标围标识别（多家标书雷同比对、报价异常规律）不在本次范围内。
这个命名冲突尚未在组织层面澄清，见 §8 的 B4。

**已定的边界：只做每家独立打分，不做跨家对比评审。**
系统对每家分别评分，页面④把结果并排展示供人比较，但系统本身不产出「A 比 B 好在哪」这类判断。
（2026-08-18 决策。提出过增加一道跨家对比调用，已明确不做，不要再往这个方向加。）

## 1. 背景：这次到底在考什么

济南公共资源交易中心组织 AI 辅助评标测试。此前已有其他厂商完成第一轮，我方本次是争取到的第二次参与机会。
（依据：录音）

**关键认知：本次测试的主要考核项不是打分准不准，而是系统能否在可接受时间内真实跑完。**

依据（均来自录音）：客户第一轮收到的竞品测试报告中没有分数，只有性能数据（两轮各耗时多久、
跑在什么卡上、占用多大显存）；竞品成绩为一个项目 50 分钟；
客户表示会现场盯着跑，以确认不是预跑好结果当场播放。

**「50 分钟」按全部投标人计**（2026-08-19 决策），本次即 12 家。

**语料体量（依据：实测）**：本次项目 12 家技术标合计 **1047 万字**（`get_text()` 口径，含空白字符），
单家 29 万~226 万字，平均 87 万字。全部为 PDF，共 241 个文件（每家 20 个，含 1 个封面）。

体量数据来源为 `原始资料/实际测试工程文件/` 下的真实文件，用 PyMuPDF 抽取正文字数统计得到。

**本文出现三个字数，口径不同，不是互相矛盾**（越往下越窄）：

| 数值 | 口径 | 出现在 |
|---|---|---|
| 1047 万字 | `get_text()` 整页文本，含空白与换行 | 本节 |
| 1006.7 万字 | 视觉行拼接后去空白 | 仅用于核对差额 |
| **981.9 万字** | **切块后落进 `text` 字段的正文**，标题行只进 `path` 不进 `text` | §10.1、§7 的 T0 |

送进模型的是最后一个。前两个只在讨论抽取损耗时才有意义。
录音中提到的「客户实测一个项目 4000 万字量级」未在本项目得到印证，
可能指更大的项目或包含商务标；本文不再引用该数字。

因此考核项按优先级排列：

| 优先级 | 考核项 | 判定标准 |
|---|---|---|
| P0 | 真实跑完，不作弊 | 客户现场盯着跑，界面需实时反映进度，**不得预跑投标文件的评审结果**。评分表与检索词属离线准备物，不在此限，界线见 §1.1 |
| P0 | 吞吐量 | **全部** 投标人标书总耗时 ≤ 50 分钟（越小越好）。本次为 12 家 / 228 次调用，约束等价于「单次耗时 ÷ 并发路数 ≤ 13.2 秒」 |
| P0 | 档位不能错 | 应得 5 分的项不能判成 8 分。档位内 1 分之差可接受 |
| P1 | 判分有据可查 | 每个判分必须给出投标文件原文引用及其章节出处 |
| P2 | 分数与专家一致 | 本次不追求。依据：2026-08-19 客户口径「先测一测就行，起码有个结果就行」。报告中正常给分，但交付的是**可追溯的判分**，分数校准是第二阶段。见 §6 阶段三 |

### 1.1 哪些能提前准备，哪些必须现场跑

这条界线在测试当天会被问到，先写清楚。（依据：2026-08-19 电话沟通）

**可以提前准备（离线产出，不计入 50 分钟）：**

- 从招标文件抽出的评分表：19 项、分值、三档区间
- 每个评分项的检索维度（`aspects`）与同义词扩展
- 项目特征摘要

理由：这三样只依赖招标文件。**招标文件是公开发布的，与任何一家投标文件无关**，
提前处理它不构成对评审结果的预知。竞品同样是在测试之前自己拆好的。
产出物落在 `config/projects/<项目名>.yaml`，测试当天直接读。

**必须现场跑（计入 50 分钟）：**

- S1 投标文件入库、S2 证据定位、S3 逐项评审、S4 汇总出报告

**计时起点：投标文件上传完成后、点下页面①的「下一步：解析」那一刻。**
不是页面③出现的时候——页面①点完就开跑 S1，S1 属于现场处理投标文件，必须计入。
因此**页面①点完「下一步：解析」就要显示计时器**，一直延续到页面③、④。

这个数当天一定会被问，先定死。好消息是 S1 很便宜：**实测 240 个 PDF，
单线程抽取加切分 39.4 秒，占 50 分钟预算的 1.3%**（复现：§10.1 的两条命令）。
所以起点定得保守一些不影响达标。

**这就是作弊的界线**：预先跑出投标文件的评审结果、当场播放，是作弊；
提前准备评分规则，不是。§1 表中 P0「真实跑完，不作弊」针对的是前者。

因此页面③（见 `docs/ui-spec.md`）的实时滚动只需覆盖 S1~S4；页面②确认的是已准备好的评分表，
人工在此核对，不是当场生成。

## 2. 术语表

本文档内所有专有名词在此定义。文档正文不使用未在此定义的缩写或代号。

| 术语 | 定义 |
|---|---|
| **招标文件** | 甲方（招标人）发布的文件。其中含「评标办法」章节，规定每个评分项多少分、什么情况得几分。本系统评分规则的唯一来源。 |
| **投标文件** | 投标人提交的应答文件。本次只处理其中的**技术部分**，商务部分明确不处理。（依据：录音）**实际到手的技术标全部是 PDF**，每家 20 个文件、文件名与评分项一一对应，见 §2.1。（依据：实测） |
| **福莱通** | 完成本次测试第一轮的另一家厂商。其产出的 `拆分评审项.xlsx`（评分项拆成要素与权重）**不进入本系统运行流程**，但作为离线对照物仍有明确用途，逐列盘点见 §2.3。 |
| **投标人 / bidder** | 参与同一个项目投标的一家单位。本次实测项目有 **12 家**。系统对每家分别跑一遍 S1/S2/S3。**`bidder` 的取值 = 投标文件所在的一级目录名原样照抄**，例 `中冶建工集团有限公司8010856`（尾部数字是投标系统给的投标编号，一并保留）。它是 `docs/data-contract.md` 里报告数据 `matrix` 与 `totals` 的键，12 家写法必须一致，不得截断或改写。 |
| **评分项** | 招标文件评标办法里的一条打分条目，例如「施工方案及技术措施，8 分」。**评分的唯一依据。** 本次共 19 项，合计 100 分。 |
| **档位** | 一个评分项内部的分数梯度。本项目招标文件对全部 19 项统一采用**三档**：一般 / 良 / 优，每档给一个**分数区间**而非单一分值，例如「施工方案及技术措施」为 1-3 分 / 3-6 分 / 6-8 分。（依据：实测） |
| **项目特征摘要** | S0 从招标文件中抽出的 300~500 字概述：工程类型、规模、地质水文条件、招标文件点名的重难点。**注入每一次 S3 调用**，是判断「针对性」这一评分维度的前提。见 §3.4。 |
| **评审点** | 本系统预置的能力清单条目，共 114 条，来自甲方提供的 `评审点.md`。**它不是评分规则**，只提供该主题的检索关键词。**本项目用不上**——评分项与投标文件由 GUID 直接绑定（§2.1），不需要评审点做中介。是否保留见 `docs/issues.md` P2。 |
| **映射** | 把招标文件的「评分项」对应到系统的「评审点」以取得检索关键词，一个项目一份配置。**本项目不需要映射**——评分项与投标文件由 GUID 直接绑定（§2.1）。该词只在讨论换项目时的降级路径时出现。 |
| **GUID 绑定** | 评分项与投标 PDF 通过文件名尾部的 GUID 一一对应，见 §2.1。本项目最重要的结构事实。 |
| **检索维度 / aspects** | 一个评分项拆出的 3~5 条检索角度，例：「进度管理方案」拆出「施工进度计划编制与关键路径分析」等。**招标文件里没有这一层**，由我方从评分描述推导。**它只是 S2 的检索词来源，不带权重、不参与判分**——早先设计里的「要素 / 二级要素加权定分」已于 2026-08-19 否决，理由见 `docs/data-contract.md`。 |
| **同义词扩展** | 为检索词补充标书实际会用的说法，例如检索维度写「S 曲线」而标书写「香蕉曲线」。检索不负责猜同义词，全靠这里补。见 §3.2 红线二。 |
| **章节块** | 投标文件切开后的最小单位，系统的检索和引用都以它为单位。docx 按 Word 标题层级切；PDF 按行首编号形式定层级、按相对满行宽区分标题与正文，见 §3.7。 |
| **证据单元** | 一个章节块的直接父章节及其下全部子块。S2 按证据单元整段收取，不收零散块。见 §3.2。 |
| **证据包** | 某个评分项在某家投标文件里检索定位到的若干证据单元，字数受 budget 约束。送给大模型的实际输入。 |
| **证据字数上限 / budget** | 单个证据包允许的最大字数。**按评分项分值分配，不是全项统一常数**——基准 3000 字、19 项、总分 100 时，20 分项取 6000（触上限）、3 分项取 1710，算式与上下限见 `docs/data-contract.md`。代码位置：`src/s2_locate.py` 的 `BUDGET`（现为统一常数，T8 改为按分值分配）。**这是全系统的算力开关**：调大则精度升、耗时升。 |
| **锚点词** | 一组检索词中在本次语料里最罕见的那一个，代表该主题的领域特征。锚点词未出现在某章节块中，该块不作为证据候选。 |
| **DF / DF 占比** | 文档频率。一个词出现在多少个章节块里（DF），除以章节块总数即 DF 占比。占比越低区分度越高（越低越好）。系统用 DF 占比而非 IDF 绝对值设阈值，原因见 §3.2 红线一。 |
| **IDF** | 逆文档频率，由 DF 换算而来，用作打分权重。一个词越罕见 IDF 越高（越高越有区分度）。 |
| **压缩比** | **全部投标文件原文总字数 ÷ 全部证据包总字数**，单位为倍，越大越好。**只作为报告中的描述性指标，不作为验收门槛**——证据字数受 budget 硬约束，该值几乎完全由 budget 决定，量不出检索准不准。下界 = 总字数 ÷ (投标人数 × 全部 19 项的 budget 之和)，基准 3000 时 budget 之和为 51,960 字/家，下界约 16.8 倍。验收改用 §6 阶段一的三条效果指标。 |
| **未命中** | 某评分项在某家投标文件中检索不到任何合格证据，判 0 分。**未命中分两种，判 0 分的可信度完全不同**，由证据包的 `pool_sections`（该项对应 PDF 切出的章节块数）区分：`pool_sections == 0` 是**没这个文件**，该家确实没写，判 0 分正确且可信；`pool_sections > 0` 是**检索没找到**——文件在、内容在，判 0 分有把「写了」判成「没写」的风险，撞 §1 的 P0「档位不能错」，因此必须标出来人工复核。两者在数据层由评审结果的 `miss_reason`（`no_file` / `not_found`）区分，字段规格见 `docs/data-contract.md` 第 6 节。 |
| **未评定** | 与「未命中」完全不同：指调用大模型失败（重试耗尽后仍格式错、超时或拒答），系统**没能给出判断**。不得记 0 分，须在报告中单列。见 §3.6 与 `docs/data-contract.md`。 |
| **降级 / fallback** | 按细粒度检索词（`aspects` 条目）检索不到证据时，退到评分项名一级的检索词重新检索。检索到的证据算弱证据，会拉低 `confidence`。 |
| **S0~S4** | 系统的五个处理阶段，见 §3。 |

### 2.1 评分项与投标文件的绑定关系（本项目最重要的结构事实）

**评分项和投标文件是一一绑定的，不需要检索去猜、也不需要人工映射。**（依据：实测）

招标文件评标办法里每个评分项的描述，结尾都有一句「相关标书内容在《某某方案》中体现」；
投标系统据此把每家的技术标拆成固定的 20 个 PDF，文件名即评分项名，
文件名尾部带一个 GUID：

```
评分项（招标文件 p33~p37）      投标 PDF 文件名
设计任务书优化 20.0 分      ←→  设计任务书优化75BD5598-9F76-4E3B-8A0A-D494380D4D9D.pdf
进度管理方案   4.0 分       ←→  进度管理方案108D538F-85B8-4C7D-B32C-F6ACDAA187B9.pdf
```

- **12 家投标人的 20 个文件名完全一致**，是投标系统的固定模板，不是巧合。
- 20 个文件中 19 个对应评分项，第 20 个是封面（无分值）。
- **绑定有两条独立的路，任一条成立即可，不依赖外部提供的 xlsx：**
  1. **按名匹配**（主路）：招标文件的评分项名与 PDF 文件名前缀唯一对应，实测 19/19，
     未匹配的文件只有「封面」。文件名被系统截断到约 14 字，因此用前缀匹配而非全等。
  2. **按 GUID 匹配**（加固）：文件名尾部 GUID 与 `拆分评审项.xlsx` 的 `pb_item_guid` 相同。
     这条依赖拿得到那份 xlsx，正式测试时不作为前提（见 `docs/issues.md` 已决事项）。

**这条事实的后果：**「从一家 87 万字的标书里检索出某评分项的证据」这个问题，
降级成「打开对应的那一个 PDF（平均 5.5 万字）」。跨文件定位不再需要算法。
S2 的作用相应收窄为**在单个 PDF 内部按检索维度定位段落**，见 §3。

核对过程与证据见 `docs/findings-招标文件核对.md`，复现脚本 `scripts/verify_scoring_table.py`。

> **换项目时的降级路径**：以上绑定依赖投标系统按评分项拆分文件并以评分项名命名。
> 若换一个不这么拆的项目（例如整本技术标只有一个 PDF），按名匹配失效，
> 需退回「评分项 → 评审点 → 检索关键词」的人工映射路线，评审点库的编号规则见 `docs/findings-原始资料缺陷.md` 第 6 节。
> 该路线是否需要保留，见 `docs/issues.md` P2。

### 2.2 状态词判定标准

本文档及后续进度同步中，「已完成 / 进行中 / 未开始」按以下标准判定，不按主观感觉：

- **已完成**：代码已写、已在**代表性数据**上跑通、输出结果已人工检查过一遍。三者缺一不算。
- **进行中**：代码已开始写，但尚未跑通。
- **未开始**：无代码，或仅有本文档中的设计描述。

「代表性数据」指能触发该模块所有代码路径的真实文件，不要求与最终业务领域一致。
**代码跑通与效果达标是两件事**，效果指标单独在 §6 的完成判定里写明。

§8 阻塞项另用一套词（待确认 / 待申请 / 待澄清 / 待指派），含义在 §8 表内逐条给出解除条件，
与本节三档状态无关，不要混用。

## 3. 系统架构

五个阶段，串成一条流水线。每个阶段的中间产物落盘为 JSON/YAML 文件，可单独运行、单独检查、单独重跑。

```
                  ┌─> 评分表.yaml ──────┐
招标文件.pdf ─S0──┤                     │
（离线，见 §1.1） └─> 项目特征摘要.md ──┼──> S3 ──> 评审结果.json ──S4──> 报告
                                       │      ↑
投标文件*.pdf ──S1──> 章节树.json ──S2──> 证据包.json
（按 GUID 绑定到评分项，见 §2.1）      （每家投标人各跑一遍 S1/S2/S3）
```

虚线以上的 S0 在测试前离线跑完，只有 S1~S4 计入 §1 的 50 分钟。

| 阶段 | 做什么 | 为什么这么做 |
|---|---|---|
| **S0** 抽招标信息 | ① 从招标文件 PDF 抽出评分表（19 项、分值、三档区间），再按评分描述拆出每项的检索维度（`aspects`）；② 抽项目特征摘要。**人工确认后存盘。** | **离线执行，不计入 50 分钟**（§1.1）。因此不要求全自动、不要求当天跑通——人 + AI 协作产出一份 yaml、人工核一遍即可。评分表由我方自产，不依赖投标系统提供的 xlsx（2026-08-19 决策）。抽取目标明确：核对已证明 19 项、分值、三档区间全部是招标文件原文（19/19 一致，见 `docs/findings-招标文件核对.md`）。 |
| **S1** 投标文件入库 | 把每家的 20 个技术标 PDF 切成章节块 | 切分策略已定案（2026-08-19 实测）：**编号形式定层级 + 相对满行宽定标题**，见 §3.7。真实 PDF 无书签、单一字号、无加粗，编号是唯一可用的结构信号。**已实现**（T0，`src/s1_ingest.py`），见 §10.1 运行命令。 |
| **S2** 证据定位 | 在**评分项对应的那一个 PDF 内部**，按检索维度检索出证据单元，组成证据包，字数受 budget 约束（budget 按该项分值分配，见 §4） | 跨文件定位已由 GUID 绑定解决（§2.1），S2 只负责文件内压缩：把单个 PDF 平均 5.5 万字压到几千字。**这仍然是算力开关**——12 家 × 19 项 = 228 次调用，若整份 PDF 直接送模型，输入总量约 1047 万字。 |
| **S3** 逐项评审 | 每个证据包 + 项目特征摘要调一次大模型，输出判分、理由、引用编号 | 每项独立无状态，天然可并行。这是把总耗时压下去的最直接手段。 |
| **S4** 汇总出报告 | 多家并排对比表 + 逐项明细 + 性能数据 | 客户的实际交付物。注意是并排展示，不是系统做对比判断，见 §0。 |

**规模基数**：12 家 × 19 项 = **228 次 S3 调用**。此前文档中的「570 次」基于 3~5 家 × 114 项，已作废。

### 3.0 这是流水线，不是 agent

**本系统不使用任何 agent 框架，不做工具调用循环，不做记忆与自我反思。**
S0~S4 的实现形态是**五个可单独运行、中间产物落盘的脚本**，用普通的并发调度串起来。
（2026-08-18 决策，依据：录音「现在的 Harness 太重了…搭个基础工具脚本，用极简模式可能直接就行」。
想引入 agent 框架之前，先说明哪个环节需要模型自主决策。）

理由：S3 是 228 次**独立、无状态、固定流程**的调用，每次的输入在调用前已完全确定
（证据包 + 项目特征摘要 + 档位描述），输出结构也已固定。**没有任何需要模型自己决定
「下一步干什么」的环节。** 而代价是实打实的：多轮工具调用让单项耗时翻倍以上，
调用总数从 228 涨到 900 多，§6 阶段二那个「单次耗时 ÷ 并发路数 ≤ 13.2 秒」的约束
收紧到 3.3 秒；循环轮数不固定还意味着总耗时无法预估，而页面③要显示「预计剩余」。
**吞吐量是 P0，分数准确度是 P2，用 P0 换 P2 算不过来。**

**这不是原则问题，是本次约束下的取舍。** 任务里确实有三处真正的自主决策点
（未命中时自主换词重检索、证据不足时主动索取更多、判分后自检），
它们各自的价值、以及「什么条件下该改回去」的具体触发条件，登记在 `docs/issues.md`。
最值得先试的一处：T9 实测后若单次调用很快、预算有富余，**只对未命中的项**加一轮自主重检索。

**对外材料里出现「智能体」「调用 Skill」这类措辞时，注意它指的是本流水线，不是 agent 循环。**
2026-08-19 辅助评审流程图里「辅助评审智能体」一个方框对应本文的 S1+S2+S3+S4 全部，
「调用 Skill」对应 S0 的离线拆分。命名口径分歧已登记在 `docs/issues.md` P1——
对外这么说没问题，但照着那张图去搭 agent 框架就是架构分歧。


### 3.1 当前实现与目标架构的差异（重要，动手前必读）

上面的架构图描述的是**目标状态**。S1（PDF 入库）已由 T0 完成（`src/s1_ingest.py` 支持 PDF，
真实数据 240 个投标 PDF 已跑通）；S2 尚跑在**软件信息化类样例**上，不是真实的工程施工类文件。
剩余差异如下：

| | 目标状态 | 当前实现 |
|---|---|---|
| S2 的评分项来源 | S0 产出的 `评分表.yaml`，19 项，带分值、三档区间与检索维度 | `config/review_points.yaml`，114 个评审点，只有名称和关键词 |
| S2 的检索范围 | 评分项对应的**单个 PDF** 内部（GUID 绑定，§2.1） | 一家的全部章节块（2121 块）混在一起检索 |
| S2 的输出 | 完整证据包，含 `bidder`、`item_id` | 缺 `bidder` 和 `item_id`（只有 `point_id`），因为尚不支持多家 |
| 跑一次的规模 | 12 家 × 19 项 = 228 次 | 1 家 × 114 项 |
| 项目特征摘要 | 注入每次 S3 调用 | 不存在，S0 未做 |

**所以：跑 §10 那三条命令，用的是 `原始资料/公司的临时样例文件仅作参考/` 下的软件类样例，
得到的 `located.json` 是 `docs/data-contract.md`「证据包」结构的子集，不是最终形态。**
它验证的是检索算法本身能不能跑（§3.2 三条红线由 `tests/test_s2_regression.py` 守住），
不代表在真实工程标书上的效果——效果验证的前提是 S2 适配多投标人（§7 的 T8）。

### 3.2 三条设计红线（摘要，全文见 `docs/retrieval-design.md`）

以下三条是 S2 在真实文件上验证出来的结论，**每条都有回归测试守着**
（`tests/test_s2_regression.py`）。改 `src/s2_locate.py` 之前先跑 `pytest`，
再去 [`docs/retrieval-design.md`](docs/retrieval-design.md) 按每条下面的「复现方式」
把反例跑出来看一眼——那份文件里有完整论证、实测反例和复现步骤。

1. **词权重必须用 DF 占比，不能用词频、覆盖率，也不能用 IDF 绝对值。**
   通用词（方案 / 措施 / 施工）没有区分度；IDF 绝对值随语料篇数漂移，换一批标书就得重调阈值。
   当前阈值 `MAX_DF_RATIO = 0.22`、`ANCHOR_DF_RATIO = 0.05`。
   **DF 统计基取该家全部 20 个 PDF**（约 3,635 块），不是单个 PDF、也不是 12 家合池。
2. **锚点词只取最罕见的那一个；DF 为 0 时直接判未命中，不换词。**
   第二半反直觉，是一次错误修复换来的：DF=0 意味着这个概念在本份标书里根本不存在，
   它是最强的信号，不是需要绕开的问题。同义词靠评分表的 `synonyms` 字段补，不靠检索去猜。
3. **必须允许未命中**，由两道独立防线保证（锚点 DF=0、`MIN_SCORE` 分数门槛）。
   投标文件没写这一项时，正确行为是返回零证据、判 0 分——硬凑一段不相关原文喂给模型，
   正是「应得 5 分判成 8 分」的来源，而那是 §1 的 P0 红线。

**不用 BM25、不用向量检索**，理由见 `docs/retrieval-design.md`：BM25 的增益（词频饱和 +
长度归一化）在本项目的章节块粒度上基本不起作用，且它是纯打分模型，给不了红线二的一票否决；
向量检索解决的是语义近似，而本任务要的是「这段有没有写深基坑」这种字面判定，
还要额外付出模型下载、显存和索引构建的耗时——全都要从 50 分钟预算里扣。

### 3.3 证据按父章节整段收取

章节块中位数只有 100~300 字，一个评分项的内容常横跨十几个相邻小节，逐块收会得到一堆
互不相邻的碎片。因此 **S2 在细粒度块上检索，收取时按整个父章节收**。

用「直接父章节」而不是固定的第 N 级标题：投标文件标题深度各不相同。
228 个真实 PDF 上实测过固定层级方案，单元字数 P90 达 23,003 字、最大 278,553 字
（budget 才几千字），**在真实数据上彻底失效**。直接父章节自适应，实测 P90 为 2,659 字，
落在 budget 之下，超出 budget 的只有 8.2%。详见 `docs/retrieval-design.md` 与
`docs/findings-pdf切分探针.md`。

### 3.4 项目特征摘要：判「针对性」的前提

评分档位**在软件信息化类标书里**普遍长这样：「5 分：阶段划分清晰、**针对本项目**、有规范依据」。
录音里也明确「有没有针对这个项目提出具体的意见，这就是一维」。

**注意本项目的招标文件不长这样**：19 项统一只写「评委根据投标文件情况分为一般、良、优，
分别酌情得 X-Y 分、Y-Z 分、Z-W 分」，三档共用一段评审标准、没有逐档描述（2026-08-20 实测）。
判档位的依据因此是评分表的 `criteria` 字段（评审标准原文），不是每档一条的描述，
详见 `docs/data-contract.md` §3。「针对性」这一维依然要判，所以下面这段结论不变。

**如果 S3 的输入只有档位描述和投标文件片段，模型手里没有「这是个什么工程」的任何信息**——
河道还是房建、什么地质、工期多长、重难点在哪——它只能判「写没写」，判不了「针对不针对」。
而针对性恰恰是 5 分和 3 分的分界线。

因此 S0 除了抽评分表，还要抽一份 300~500 字的**项目特征摘要**，作为全局上下文注入每一次 S3 调用。
500 字 × 228 次约增加 8 万 token，占总量比例很小，但这是「针对性」这一维能不能判的前提。

### 3.5 防幻觉：引用用选择，不用生成

**模型不输出原文，只输出证据编号。**

证据包里的每个章节块带一个序号，模型输出 `"cite": [2, 5]`，原文由系统按序号从章节块里截取。

不这么做的话——让模型自由输出 `quote` 再回原文做字符串匹配——中文模型极大概率会改写而非
逐字复制（顺手把「三个施工段」写成「三段施工」），于是大批引用校验失败，
`confidence` 全线打折，所有项都标「建议人工复核」，信号全糊掉等于没做。

**把生成改成选择，幻觉从根上不存在**，不需要事后检测，还省下吐原文的 token。
系统仍校验编号是否在证据包范围内，越界即判该次调用失败并重试（§3.6）。

### 3.6 调用失败：先重试，重试耗尽才记未评定

228 次调用里必然有失败的：JSON 格式错、超时、模型拒答、引用编号越界。

**处理顺序是重试优先，不是直接记未评定：**

1. **重试 3 次**，退避间隔 2 秒 / 4 秒 / 8 秒。格式错误的重试请求里附上上一次的错误信息。
2. 3 次仍失败 → 该项标记为**未评定**（`status: "unrated"`），`score` 置 null。
3. **未评定不等于 0 分。** 0 分表示投标人没写，未评定表示系统没判出来——把模型的问题算成投标人的问题是错的。
4. 未评定项在页面③实时显示、在页面④单独用符号标出、在报告中单列一节，不混进分数统计。

全流程跑完后允许对所有未评定项发起一轮统一重跑，这一轮同样计入总耗时。

### 3.7 PDF 怎么切块（已定案，2026-08-19 实测）

**结论：编号形式定层级 + 相对满行宽定标题。** 完整依据、实测数据与切出来的分布在
[`docs/retrieval-design.md`](docs/retrieval-design.md)，复现脚本 `scripts/probe_pdf_structure.py`。

三句话版本：

- **PDF 无书签、全文单一字号 12.0pt、加粗行 0%**——投标系统生成 PDF 时抹平了所有格式，
  按字号或加粗推断标题完全不可行。
- **剩下的唯一信号是行首编号**，层级由编号形式直接给出（`第N章` / `一、` / `1、` / `N.N` / `（N）`，共 5 级）。
- 正文段落也大量以编号开头，靠**行长**区分：
  **匹配编号形式、且行长 < 0.8 × 本文档行长 P90（满行宽）** 的才算标题。
  阈值相对于每份文档自己的行宽，不写死绝对字数——与红线一用 DF 占比而非绝对值是同一条原则。

切出来每份 PDF 中位 111 个章节块、块字数中位 114 字，与 docx 路径同量级，
所以 `src/s2_locate.py` 不需要改。

## 4. 数据契约

**模块之间的全部接口规格在 [`docs/data-contract.md`](docs/data-contract.md)**，本节只做索引。
改那份文件里的任何结构 = 改接口，上下游要同步改；改其他任何东西都不影响别的模块。

七个结构，按数据流顺序：

| # | 结构 | 谁产出 | 谁消费 |
|---|---|---|---|
| 1 | 章节块 | S1 | S2、页面⑤ |
| 2 | 章节块全量索引 | S1 合并 | S4 |
| 3 | 评分表 | S0（离线） | S2、S3、页面② |
| 4 | 项目特征摘要 | S0（离线） | S3 |
| 5 | 证据包 | S2 | S3、页面⑤ |
| 6 | 评审结果 | S3 | S4 |
| 7 | 报告数据 | S4 | 页面④、导出 |

**四条最容易踩的约定**，先记住，细节去那份文件里看：

- **跨投标人引用一律用 `(bidder, id)` 复合键。** 12 家共用同一套 20 个文件名、
  连文件名尾部的 GUID 都相同（§2.1 的投标系统固定模板），章节块 `id` 只在单家范围内唯一。
  单用 `id` 会跳到别家的标书。
- **`0` 分和「未评定」是两件事**：前者是投标人没写或检索没找到（§3.2 红线三），
  后者是系统没判出来（§3.6）。数据层不得合并，渲染层必须用不同符号。
  **`0` 分自身还要再分一次**：`miss_reason` 为 `no_file`（没这个文件）还是 `not_found`
  （检索没找到）决定它可不可信，见 §2 术语表「未命中」。
- **要素加权定分已否决**（2026-08-19）：`tier` 由模型对着招标文件的评审标准原文（评分表的 `criteria` 字段）判定，
  `score` 由模型直接在该档区间内给出，系统只校验是否越界。
  评分表里的 `aspects` 只是 S2 的检索词来源，不带权重、不参与判分。
  理由见 data-contract.md 的「为什么不做要素加权定分」——**不要再往回加**。
- **证据字数上限 `budget` 按分值分配**（2026-08-19）：20 分的评分项判错一档的代价是
  3 分项的 6 倍多，两者不该拿同样的证据字数。总输入量不变，只改分配。

## 5. 界面与交互逻辑

**五个页面的线框与交互规格在 [`docs/ui-spec.md`](docs/ui-spec.md)**，对应任务 T5、T6。
本节只留那条谁都得知道的硬约束和页面流概览。

### 5.1 界面设计的唯一硬约束

**客户会站在旁边盯着屏幕看，判断这是不是真在跑。**（依据：录音）

因此：进度必须实时、逐项滚动、显示当前正在评哪一项和已用时间。
**一个转圈的 loading 动画等于没做。** 这是产品硬需求，不是技术细节。

「实时」的判定标准：**每完成一个评分项，1 秒内必须出现在滚动区**；
滚动区连续 30 秒无新条目时，需显示当前正在处理的项目名与已等待时长，而不是让界面看起来卡死。

### 5.2 页面流概览

```
① 新建评审  →  ② 确认招标信息  →  ③ 运行监视  →  ④ 结果并排  ⇄  ⑤ 单项详情
                   （人工介入）
```

| 页面 | 职责 | 本页最要紧的一条 |
|---|---|---|
| ① 新建评审 | 上传招标文件与 12 家投标文件，跑 S1 回显字数 | **点「下一步：解析」即启动计时器**，S1 计入 50 分钟（§1.1） |
| ② 确认招标信息 | 核对评分表、项目级规则、项目特征摘要 | 全流程唯一人工介入点；也是「离线准备物当场可核」的展示位 |
| ③ 运行监视 | 逐项实时滚动，显示耗时、token、重试、未评定 | 客户盯着看的就是这一页，见 §5.1 |
| ④ 结果并排 | 12 家 × 19 项对比表 + 导出报告 | `0` 与 `—` 必须视觉可区分；导出必须含 `compute_notes` 一节 |
| ⑤ 单项详情 | 评审标准原文（`criteria`）+ 判分理由 + 引用证据 + 专家复核 | 可解释性由「理由 + 证据」承担，没有加权算式那一块 |

技术栈尚未确定（§8 的 B6）。确定之前，五个页面先做成不依赖后端的静态 HTML 原型
（假数据、可点击、可演示交互），只需现代浏览器可打开，不引入构建工具。

## 6. Roadmap

阶段之间是依赖关系，不是时间切分。每个阶段写明「做完的判定标准」，没有判定标准的阶段不算阶段。

### 阶段一：链路跑通（目标 2026-08-19 至 2026-08-20）

**做完的判定标准：用本次实测项目的招标文件 + 1 家投标文件（20 个 PDF），
端到端跑出一份带证据引用的评审结果 JSON，且满足下面三条 S2 效果指标。**

| 指标 | 门槛 | 为什么是这条 |
|---|---|---|
| 证据包非空率 | ≥ 90%（19 项中至少 18 项检索到证据） | 招标文件为每项都设了分值，专业投标人极少整项不写。大面积未命中说明检索配置错了，见 §3.2 红线三 |
| 证据总字数 | ≤ 全部 19 项 budget 之和（基准 3000 时为 51,960 字/家。**2026-08-20 实测 12 家实际 492,836 字，41,070 字/家**，未顶到上限） | 这是送进模型的实际输入量，直接决定 §1 的吞吐量 |
| 人工抽查相关性 | 随机抽 10 项，证据与评分项主题相关 | 前两条都是量，这条是唯一验质的 |

**原判定「压缩比 ≥ 20 倍」已作废。** 原因不是数字定错，是这个指标在 GUID 绑定之后失去了意义：
压缩比 = 总原文字数 ÷ 实际证据总字数，而证据字数受 budget 硬约束，
所以压缩比几乎完全由 budget 决定，**量不出检索选得准不准**。
它是从「跨一家 140 万字全文检索」那个旧设计继承来的——那时压缩比确实反映检索的选择性。
现在检索范围已由 GUID 缩到单个 PDF（§2.1），选择性由上表第三条来验。
压缩比保留为报告中的**描述性指标**，算法见 §2 术语表，不作为验收门槛。

**已经在手的基线**（状态词判定标准见 §2.2：已完成 = 代码写了 + 代表性数据跑通 +
人工检查过输出，三者缺一不算）：

| 已完成 | 证据 |
|---|---|
| S1 入库（**docx 路径**） | 10 个 docx 样例跑通，输出 2121 个章节块并人工检查。**该路径对真实文件不适用**，真实文件是 PDF |
| S1 入库（**PDF 路径**，T0） | 12 家 240 个 PDF 实测跑通，32,129 块 / 9,819,249 字 / 39.4 秒；按家分别入库，`level`/`path`/`item_guid`/`page` 齐全 |
| S2 证据定位（算法） | 算法跑通、输出已人工抽查；三条红线由 §3.2 固化，`tests/test_s2_regression.py` 13 项断言全绿 |
| 招标文件与评分表核对 | 19 项 / 100 分 / 三档区间 19/19 一致，见 `docs/findings-招标文件核对.md`，复现脚本 `scripts/verify_scoring_table.py` |
| 评审点库生成 | 114 个评审点已生成到 `config/review_points.yaml`。**本项目用不上**，见 §2.1 |

T2（S3 单项跑通）、T6（S4 报告输出）。

两张表并存过一段时间，措辞已经开始漂移，故合并到 §7。

### 阶段二：性能达标（目标 2026-08-21）

**做完的判定标准：12 家标书全量跑完（228 次调用），总耗时 ≤ 50 分钟（越小越好），
全程无中断，中途杀进程后能从断点续跑，且未评定项为 0。**

「全程无中断」按端点形态取不同的可判定表述——**因为 B3 若为远程托管，我方采集不到显存，
「不因显存溢出中断」这条既无法判定也无从预防**：

| 端点形态 | 判定表述 |
|---|---|
| 本地/可观测算力 | 不因显存溢出中断，且峰值显存记入报告 |
| 远程托管端点 | 不因端点限流、超时或连接中断而失败；触发限流时按 §3.6 重试并记入 `retries` |

端点形态取决于 B2，见 §8。

「≤ 50 分钟」按全部投标人计（2026-08-19 决策），本次即 12 家。
**该预算只装 S1~S4，不含 S0 的离线准备**，界线见 §1.1。

**这个预算比按 114 项测算时宽松得多。** 约束是 `单次耗时 ÷ 并发路数 ≤ 13.2 秒`：

| 单次耗时 | 并发 2 路 | 并发 4 路 | 并发 8 路 |
|---|---|---|---|
| 15 秒 | 28.5 分 ✓ | 14.3 分 ✓ | 7.1 分 ✓ |
| 30 秒 | 57 分 ✗ | 28.5 分 ✓ | 14.3 分 ✓ |
| 60 秒 | 114 分 ✗ | 57 分 ✗ | 28.5 分 ✓ |

**风险点因此从「调用次数太多」转移到「并发路数够不够」**，而并发路数受显存限制。
T9 单点实测的重点相应改变：不只测单次耗时，要测并发 N 路时显存是否扛得住。

| 任务 | 完成判定 |
|---|---|
| 模型单点性能实测（T9） | 拿到单次调用的真实耗时与显存占用，据此重算并发路数与 budget |
| 两层并发（投标人 × 评分项） | 并发路数可配置，实测吞吐量随路数提升 |
| 重试与未评定处理 | 按 §3.6 实现；人为注入格式错误时能触发重试并最终标记未评定 |
| budget 调优 | 在 50 分钟预算内取到最大的基准 budget（字数越大精度越高），并按分值分配到 19 项 |
| 性能埋点 | 每次调用的输入/输出 token、耗时落盘；显存与卡型号若可采集则写入报告，不可采集则记「未采集」并注明原因 |
| 断点续跑 | 杀进程后重启能从断点继续，不重跑已完成项。**这是本阶段完成判定的一部分，不是可选功能**（见本节开头的判定标准），同时是对 50 分钟这条 P0 的风险对冲：客户现场盯着跑，跑到第 9 家崩了、没有续跑就得从头再来，直接撞穿预算。**分两半实现，可砍的只有后半**：① S3 结果逐项落盘（成本接近零，就是别攒在内存里最后一次性写）——**不可砍**；② 启动时自动扫描已完成项、跳过并重排并发槽——落后了可退化为当天手工指定从第几家继续。工作量按半天估，不是半小时：并发调度要处理「已完成项不占并发槽」，还要和 §3.6 那轮「全跑完后统一重跑 unrated」对齐 |

**2026-08-20 已有首轮实测，取代下面的推算（推算段保留供对照，勿据此排期）：**
智能体工厂端点，3 家 57 项串行实测：**每家 29~42 秒**，单次调用中位 1.6 秒，
0 未评定，重试率 5.5%。**外推 12 家串行约 7.5 分钟，不开并发即满足 50 分钟预算，富余约 6.7 倍。**
（该数据为清理 agent 人格后所得；清理前为每家 73 秒，提速来自模型输出量降到 1/5。）
复现见 `docs/findings-智能体工厂端点.md`。因此「并发路数够不够」不再是本阶段的风险点，
T9 的重点收窄为：并发是否仍需要、以及端点在连续 228 次调用下是否稳定。

**以下为 2026-08-19 的推算，已被上面的实测取代：**
按每次 8 秒、并发 8 路计，228 次调用约 3.8 分钟。但 **8 秒这个数没有任何依据**。
3000 字输入在 20B 级模型上更可能是 15~30 秒。按上表，30 秒/次需要并发 ≥ 3 路才达标，
60 秒/次需要 ≥ 5 路。**并发路数能不能上去取决于显存**，这是 T9 要测的核心。
所以 T9 必须是 B2 解除后的第一件事，不能等全链路跑通才发现并发上不去——
那时候只剩砍 budget 一条路。

**另一笔账：不压缩会怎样。** 12 家技术标合计 1047 万字。若把每个评分项对应的整份 PDF
直接送模型，输入总量约 1047 万字（≈700 万 token）。压到 budget 3000 字后，
12 家 × 51,960 字 ≈ 62 万字，是压缩比 16.8 倍——**这是基准 3000 时的下界**，
因为 budget 是上限不是目标，着墨少的评分项装不满，实际压缩比会更高。
**注意这个数由 budget 直接决定，不反映检索质量**，所以阶段一的验收用的是上面那三条，不是它。

### 阶段三：分数校准（本次测试不做）

**做完的判定标准：与专家人工评分的档位一致率 ≥ 90%（越大越好）。
「档位一致」指系统判分与专家判分落在同一个 `tier` 内，不要求分值相同。**

本阶段依赖阶段一二产出的复核数据（页面⑤的改判记录，见 `docs/ui-spec.md`），且需要业务专家参与定义
「什么叫写得一般」这类主观档位的可判定标准。
**本次测试明确不做，报告中需说明这是第二阶段工作。**（依据：录音，会上已明确第一步只解决识别与对分）
